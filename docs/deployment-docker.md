# HLViewer — Розгортання через Docker

Повна інструкція розгортання системи на сервері з Docker.

> **Кому цей документ.** Адміністратору сервера, який піднімає HLViewer «з нуля».
> Після успішного розгортання переходьте до [initial-setup.md](initial-setup.md) — там
> первинне налаштування філій, ЛУМГ, ліній, DPD-промисловості тощо через адмін-панель.

---

## 1. Передумови на сервері

```bash
apt update && apt install -y docker.io docker-compose-v2 git
```

Перевірка версій:

```bash
docker --version        # очікується Docker 24+
docker compose version  # очікується v2.x (саме "docker compose", не "docker-compose")
git --version
```

---

## 2. Отримати файли проєкту

Клонуємо два репозиторії (потрібен доступ до інтернету на сервері):

```bash
mkdir -p /opt/hlviewer
cd /opt/hlviewer

# Бекенд: FastAPI + БД + scheduler
git clone https://github.com/volodymyr-vereshchak/HLViewer.git  HLViewer
# Фронтенд: зібраний dist лежить у репозиторії, у контейнері нічого не збирається
git clone https://github.com/volodymyr-vereshchak/hl_frontend.git hl_frontend
```

> **Оновлення фронтенду.** Образ бере готовий `dist/` з репозиторію, тому
> `git pull` у `hl_frontend` + `docker compose up -d --build frontend_v2`
> достатньо. Якщо змінювали код фронтенду локально — спершу `npm run build`
> і закомітити `dist/`, інакше поїде стара збірка.

## 3. Налаштування `.env`

Усі секрети та параметри читаються з `.env` у корені бекенду. У `docker-compose.yml`
секретів немає — тільки посилання на цей файл.

```bash
nano /opt/hlviewer/HLViewer/.env
```

Вставити вміст (замінити значення, позначені `ЗАМІНИТИ` / `YOUR_...`):

```env
# ── База даних ────────────────────────────────────────────────────────────────
POSTGRES_DB=hostlib_db_v2
POSTGRES_USER=YOUR_DB_USER
POSTGRES_PASSWORD=YOUR_DB_PASSWORD
# DB_HOST / DB_PORT нижче — для доступу до БД з ХОСТА (порт 5434 проброшено назовні).
# УСЕРЕДИНІ контейнерів docker-compose.yml ПЕРЕВИЗНАЧАЄ їх на db_v2:5432 (ім'я сервісу
# в мережі Docker), тож бекенд у контейнері ходить до сервісу db_v2 — міняти не треба.
DB_HOST=localhost
DB_PORT=5434

# ── Автентифікація ────────────────────────────────────────────────────────────
# JWT_SECRET — обов'язковий, застосунок не стартує без нього (fail-closed).
# Згенерувати: openssl rand -hex 32
JWT_SECRET=ЗАМІНИТИ_openssl_rand_-hex_32
# Адмін-акаунт — авто-сідується при старті. Має доступ до адмін-панелі.
ADMIN_USERNAME=admin
ADMIN_PASSWORD=ЗАМІНИТИ_ПАРОЛЬ
# Viewer-акаунт — авто-сідується при старті з роллю `viewer`. Viewer БЕЗ призначених
# філій бачить УСІ філії; щоб обмежити — призначте філії в адмін-панелі (вкладка
# «Користувачі»). Стара роль `viewer_all` автоматично мігрує в `viewer` при старті.
DEFAULT_USERNAME=viewer
DEFAULT_PASSWORD=ЗАМІНИТИ_ПАРОЛЬ
# AUTO_LOGIN — значення залежить від LDAP_ENABLED (див. блок LDAP нижче):
#  • LDAP вимкнено: true = автоматичний вхід як DEFAULT_USERNAME без вікна логіну
#    (зручно для внутрішнього стенду); false = звичайне вікно входу.
#  • LDAP увімкнено: автоматичний вхід НЕ працює (всі бачать вікно входу); true/false
#    керує лише тим, як реєструються НОВІ доменні користувачі (див. нижче).
AUTO_LOGIN=true

# ── LDAP (доменна автентифікація) — необов'язково ────────────────────────────
# LDAP_ENABLED=true — користувачі можуть входити СВОЇМИ доменними логіном/паролем.
# Пароль перевіряється прямим bind'ом у Active Directory як username@LDAP_DOMAIN —
# сервісний акаунт не потрібен, групи AD не читаються. Права завжди беруться з БД
# застосунку (роль + філії призначає адмін у вкладці «Користувачі»).
# Локальні паролі (admin, viewer тощо) працюють ПАРАЛЕЛЬНО — LDAP їх не вимикає.
#
# Матриця режимів для НОВОГО доменного користувача (немає в БД застосунку):
#  LDAP_ENABLED=true + AUTO_LOGIN=true  → авто-створюється АКТИВНИМ viewer'ом без
#    обмежень по філіях і одразу входить (адмін потім може звузити доступ).
#  LDAP_ENABLED=true + AUTO_LOGIN=false → створюється НЕАКТИВНИМ; на формі
#    «Обліковий запис створено. Зверніться до адміністратора» — адмін активує
#    його і призначає роль/філії у вкладці «Користувачі» (див. initial-setup.md §2).
# Існуючий запис у БД завжди має пріоритет: деактивований користувач НЕ ввійде
# навіть із вірним доменним паролем.
#
# Значення LDAP_SERVER/LDAP_DOMAIN можна дізнатися на будь-якій доменній
# Windows-машині: nltest /dsgetdc:%USERDNSDOMAIN% покаже контролер домену,
# а `whoami /upn` — UPN-суфікс (частина після @; саме він іде в LDAP_DOMAIN
# і може ВІДРІЗНЯТИСЯ від DNS-імені домену).
LDAP_ENABLED=false
# Адреса контролера домену: ldap://dc.example.local або ldaps://dc.example.local:636
LDAP_SERVER=
# UPN-суфікс домену (те, що після @ у доменному логіні), напр. example.local
LDAP_DOMAIN=
# true — з'єднання по LDAPS (порт 636); false — звичайний LDAP (порт 389)
LDAP_USE_SSL=false

# ── CORS ─────────────────────────────────────────────────────────────────────
# Список дозволених джерел фронтенду. Додайте сюди IP/домен сервера з портом 3001.
CORS_ORIGINS=http://localhost:3001,http://127.0.0.1:3001,http://<IP-СЕРВЕРА>:3001

# ── Звіти ────────────────────────────────────────────────────────────────────
# Контрактна година — початок комерційної доби (напр. 07:00 → 07:00 наступного дня).
# Глобальний параметр для звітів (нічні витрати, годинні тренди). Фронтенд читає його
# через GET /config. За замовчуванням 7.
CONTRACT_HOUR=7

# ── Логи ─────────────────────────────────────────────────────────────────────
# LOG_DIR — шлях УСЕРЕДИНІ контейнера. Через bind-mount `.:/app` він відповідає
# <repo>/logs на хості, тож backend.log / backend.error.log / frontend.log —
# звичайні файли на сервері (читаються без Docker). Ротація 10 МБ × 5.
LOG_DIR=/app/logs
LOG_LEVEL=INFO
LOG_MAX_BYTES=10485760
LOG_BACKUP_COUNT=5

# ── Промисловість (DPD) — необов'язково ───────────────────────────────────────
# Макс. одночасних з'єднань до DPD API при опитуванні промисловості (за замовч. 10).
# Підвищуйте (напр. 20–30), якщо звіти по промисловості будуються повільно: низька
# межа серіалізує запити до приладів «хвилями» і збільшує загальний час.
DPD_MAX_CONCURRENCY=10

# ── Шара АС4 — необов'язково ──────────────────────────────────
# AS4_HOST_PATH — де шара змонтована НА ХОСТІ (див. розділ 6). Усередині
# контейнерів шлях завжди /mnt/as4 — саме це записано в БД, тому перенос
# шари на хості не вимагає змін у БД. За замовчуванням /mnt/as4 — задавати
# лише якщо шара на хості лежить в іншому каталозі.
#AS4_HOST_PATH=/mnt/as4
# AS4_PROPAGATION — rslave (за замовчуванням) або rprivate. Лише для хостів, де
# контейнери не стартують з помилкою «is not a shared or slave mount» (Docker
# Desktop, деякі LXC) — див. розділ 6, крок 4.
#AS4_PROPAGATION=rslave

# ── GSM-опитування — необов'язково ────────────────────────────────────────────
# Обидва шляхи відносні до робочої теки застосунку (/app у контейнері, тобто
# <repo>/ на хості через bind-mount `.:/app`), обидва мають робочі значення за
# замовчуванням — задавайте, лише щоб перенести файли в інше місце.
# POLL_LOG_DIR — журнали опитування, по одному файлу на підприємство; кожна
# нова сесія переписує свій. Їх показує кнопка журналу в «Моніторі GSM».
# AGENT_DIST_DIR — тека, з якої адмінка роздає збірку агента («Опитування →
# Агенти»). Усередині hlv-poller-<версія>.zip; кладе його
# hl_poller/build_exe.py --install, і цей файл комітиться — на офлайн-сервер
# він їде git-бандлом разом із кодом.
POLL_LOG_DIR=logs/poll
AGENT_DIST_DIR=backend/data/agent

# ── HTTPS — необов'язково ─────────────────────────────────────────────────────
# COOKIE_SECURE=true — надсилати auth-cookie лише по HTTPS. Для внутрішнього HTTP
# лишайте false, інакше cookie не встановиться і вхід не працюватиме.
COOKIE_SECURE=false
```

> **Після зміни `.env`** застосовуйте через **`docker compose up -d`** (перестворення
> контейнера) — `docker restart` НЕ перечитує `env_file`.

## 4. Запуск

```bash
cd /opt/hlviewer/HLViewer

# Одноразово на новому сервері: створити named volume для даних БД.
# Він зовнішній (external), тому compose його НЕ видаляє навіть при `down -v` —
# дані БД переживають перестворення контейнерів.
docker volume create hlviewer_pgdata_v2

# Перший білд: стягує базові образи з Docker Hub і збирає застосунок (~5–10 хв).
# Команда запуску в контейнері: alembic upgrade head → preload_db → uvicorn (8 воркерів).
docker compose up -d --build

# Стежимо за запуском
docker compose logs -f
```

Очікувана послідовність у логах:

1. `postgres_db_v2` → `database system is ready to accept connections`
2. `fastapi_app_v2` → `alembic upgrade head` → `preload_db` → `Application startup complete`
3. `scheduler_v2` → `Scheduler started`
4. `frontend_app_v2` → `nginx: start worker process`

## 6. Підключення до шари АС4 (архівні hostlib-файли)

Архівні hostlib-файли лежать на мережевій шарі. Обов'язки розділені так:

- **хост** монтує `//server/share` у локальний каталог (`/mnt/as4`) — це робота ОС, а не застосунку;
- **контейнери** `fastapi_v2` і `scheduler_v2` отримують цей каталог автоматично, лише для
  читання: рядок `${AS4_HOST_PATH:-/mnt/as4}:/mnt/as4:ro,rslave` вже є в `docker-compose.yml`.
  Правити compose руками **не потрібно**.

`rslave` означає, що монтування, яке хост зробить у цьому каталозі **пізніше**, з'явиться
і в уже запущеному контейнері. Це важливо: при завантаженні сервера Docker не чекає на
шару і може підняти контейнери раніше, ніж змонтується CIFS. Без `rslave` контейнер
назавжди (до перезапуску) лишився б із порожнім каталогом.

Шляхи в БД (таблиця `lumg_data_path`) вказують на `/mnt/as4/...` — це шлях **усередині
контейнера**. Він не змінюється, навіть якщо на хості шара лежить в іншому місці:
для цього є `AS4_HOST_PATH` у `.env`.

> ⚠️ Якщо на цьому сервері volume шари колись дописували в `docker-compose.yml` руками —
> приберіть ту правку (`git checkout -- docker-compose.yml`), інакше кожне оновлення буде
> давати конфлікт при `git pull`.

**Крок 1 — пакети для CIFS:**

```bash
apt install -y cifs-utils keyutils
```

`keyutils` потрібен ядру, щоб після обриву зв'язку заново знайти IP сервера за ім'ям
і перепідключити шару. Без нього перше монтування працює, а перепідключення — ні.

**Крок 2 — файл з обліковими даними.** Пароль не повинен лежати в `/etc/fstab`,
який читають усі:

```bash
install -d -m 700 /etc/hlviewer
cat > /etc/hlviewer/as4.cred <<'EOF'
username=SERVICE_USER
password=ЗАМІНИТИ
domain=ЗАМІНИТИ
EOF
chmod 600 /etc/hlviewer/as4.cred
```

**Крок 3 — рядок у `/etc/fstab`**, щоб шара піднімалася сама після перезавантаження:

```bash
mkdir -p /mnt/as4
nano /etc/fstab
```

```fstab
//СЕРВЕР/ШАРА  /mnt/as4  cifs  credentials=/etc/hlviewer/as4.cred,ro,_netdev,nofail,iocharset=utf8  0  0
```

`//СЕРВЕР/ШАРА` — це **весь** мережевий шлях до шари АС4, той самий, що в Windows
відкривають у провіднику (напр. `\\as4-grmu-app.naftogaz.com\ФІЛІЯ`), лише з прямими
слешами: `//as4-grmu-app.naftogaz.com/ФІЛІЯ`. Дізнатися його: `net use` на
Windows-машині, де шару підключено диском, або `Get-SmbShare` на самому файловому сервері.

- `/mnt/as4` — це корінь шари: шлях `/mnt/as4/X`, який потім вказують в адмінці,
  відповідає `\\СЕРВЕР\ШАРА\X`.
- Ім'я сервера пишіть повністю, як у прикладі вище. Коротке ім'я (`as4-grmu-app`)
  Linux може не знайти: Windows шукає його через NetBIOS, Linux — ні. Перевірка:
  `getent hosts as4-grmu-app.naftogaz.com`; якщо порожньо — вкажіть IP сервера.
- Пробіл в імені шари записується як `\040`: `\\СЕРВЕР\AS4 Archive` → `//СЕРВЕР/AS4\040Archive`.

- `ro` — застосунок у шару нічого не пише (архіви розпаковуються в `/app/hostlibs`),
  тому доступ лише на читання;
- `_netdev` — монтувати після підняття мережі;
- `nofail` — якщо шара недоступна, сервер усе одно завантажиться (без цього
  можна отримати emergency mode);
- `iocharset=utf8` — коректні кириличні імена каталогів ЄІС та файлів;
- версія SMB (`vers=`) не вказана — ядро саме обирає найновішу спільну з сервером,
  але пропонує лише **SMB 2.1 і новіші**. Це підходить для серверів від Windows 7 /
  Server 2008 R2. Якщо шара на старішому сервері (Windows XP / Server 2003 /
  Server 2008 без R2, старий NAS), спільної версії немає і `mount` падає з
  `mount error(112): Host is down`, хоча сервер живий. Тоді додайте до опцій
  `vers=2.0`, а якщо й так не монтується — `vers=1.0` (SMB1 небезпечний, лише для
  справді старих серверів). Справжню причину будь-якої помилки показує
  `dmesg | tail` одразу після невдалого `mount`.

```bash
mount -a
```

**Крок 4 — перевірка:**

```bash
findmnt /mnt/as4                            # хост бачить шару
docker exec fastapi_app_v2 ls /mnt/as4/     # контейнер бачить ту саму шару
findmnt -o TARGET,PROPAGATION /             # має бути shared (див. нижче)
```

`rslave` працює, лише якщо коренева ФС хоста змонтована як `shared` — на дистрибутивах
із systemd так за замовчуванням. Якщо там `private`, Docker відмовиться запускати
контейнер з помилкою `... is not a shared or slave mount`. Тоді виконайте
`mount --make-rshared /` і додайте цю ж команду в автозапуск (наприклад, `/etc/rc.local`).

Якщо так зробити не можна (Docker Desktop, LXC-контейнер без прав), задайте в `.env`
`AS4_PROPAGATION=rprivate`. Контейнери стартуватимуть, але шару, змонтовану після їхнього
старту, не побачать — після кожного монтування потрібен
`docker compose restart fastapi_v2 scheduler_v2`.

Остаточна перевірка — перезавантажити сервер і переконатися, що після старту
`docker exec fastapi_app_v2 ls /mnt/as4/` показує файли без жодних ручних дій.

### Якщо шара відвалилася

Симптом у `logs/backend.log` — застосунок працює, але дані перестають оновлюватися:

```
ERROR backend.hl_engine.main: Hostlib path does not exist: '/mnt/as4/...' - skipping 3 LUMGs
```

```bash
mount -a                                        # підняти шару на хості
findmnt /mnt/as4                                # переконатися, що піднялася
docker exec fastapi_app_v2 ls /mnt/as4/         # завдяки rslave контейнер бачить її одразу
```

Перезапускати контейнери не потрібно — нове монтування доходить до них саме.

Якщо шара не відвалилася, а **зависла** (`ls /mnt/as4` на хості висить або дає помилку
введення-виведення), `mount -a` нічого не зробить — спершу її треба відмонтувати:

```bash
umount -l /mnt/as4 && mount -a
```

> Контейнери, створені до появи `rslave` у `docker-compose.yml`, ще тримають старе
> монтування. Їх треба один раз перестворити: `docker compose up -d fastapi_v2 scheduler_v2`
> (оновлення з адмінки робить це саме).

## 7. Доступ контейнерів до внутрішнього REST API (DPD)

DPD API (напр. `rest-direct.zp.iot.grmu.com.ua`) знаходиться у внутрішній мережі.
Docker-контейнери за замовчуванням використовують DNS `8.8.8.8` і можуть не резолвити
внутрішні імена.

> ℹ️ URL-адреси DPD API (base URL та auth URL) і облікові дані тепер задаються **окремо
> для кожного філіалу** в адмін-панелі → вкладка «DPD Креденшали», а НЕ через env-змінні.
> Порада щодо DNS нижче лишається актуальною: контейнери мають резолвити ці внутрішні імена.

**Крок 1 — перевірити резолвінг імені на хості:**

```bash
nslookup rest-direct.BRANCH.iot.grmu.com.ua
curl -k https://rest-direct.BRANCH.iot.grmu.com.ua/api/v1/
```

Якщо хост резолвить ім'я, але контейнер — ні, причина у DNS.

**Крок 2 — знайти внутрішній DNS-сервер хоста:**

```bash
cat /etc/resolv.conf   # рядок "nameserver X.X.X.X"
```

**Варіант А — передати DNS контейнерам через Docker daemon:**

```bash
nano /etc/docker/daemon.json
```

```json
{
  "dns": ["<INTERNAL_DNS_IP>", "8.8.8.8"]
}
```

```bash
systemctl restart docker
docker compose up -d
```

**Варіант Б — прописати IP напряму у `docker-compose.yml`** (якщо внутрішній IP відомий):

```yaml
fastapi_v2:
  extra_hosts:
    - "rest-direct.BRANCH.iot.grmu.com.ua:<API_IP>"
    - "auth-direct.BRANCH.iot.grmu.com.ua:<API_IP>"
```

Перевірка з середини контейнера:

```bash
docker exec fastapi_app_v2 curl -k https://rest-direct.BRANCH.iot.grmu.com.ua/api/v1/
```

## 8. Резервне копіювання БД

> Дані БД лежать на **зовнішньому named volume `hlviewer_pgdata_v2`** (див. п.4).
> Він не видаляється навіть при `docker compose down -v`, тому перестворення контейнерів
> (`up -d`) безпечне. Перед великими операціями однаково робіть дамп.

```bash
# Дамп
docker exec postgres_db_v2 \
  pg_dump -U YOUR_DB_USER hostlib_db_v2 | gzip > backup_$(date +%Y%m%d).sql.gz

# Відновлення
gunzip -c backup_20260101.sql.gz | \
  docker exec -i postgres_db_v2 psql -U YOUR_DB_USER hostlib_db_v2
```

## 9. Логи

stdout-логи контейнерів дивляться через Docker — це найповніше джерело (вивід процесів
бекенда/scheduler + access/error-логи nginx фронтенда). Ротуються драйвером `json-file`
(10 МБ × 5):

```bash
docker compose logs -f fastapi_v2     # бекенд
docker compose logs -f frontend_v2    # nginx фронтенда
docker compose logs -f scheduler_v2   # планувальник оновлень
docker compose logs --tail 100        # всі сервіси
```

Файлові логи бекенда лежать у `<repo>/logs` (`LOG_DIR`), а журнали GSM-опитування —
у `<repo>/logs/poll` (`POLL_LOG_DIR`), по одному файлу на підприємство. Останні
зручніше дивитися з адмінки: «Опитування → Монітор GSM», кнопка журналу в рядку.
Докладно про GSM — [gsm-polling.md](gsm-polling.md).

## 10. Оновлення з адмінки («Версія програми»)

Кнопка в адмін-панелі (група «Система» → «Версія програми»), яка сама забирає
новий код з GitHub, робить копію бази, перезбирає та перезапускає програму, а
якщо нова версія не піднялась — повертає попередню. Лише для Linux + Docker;
Windows-сервер оновлюється вручну бандлами, як і раніше, — там цього не вмикайте,
і вкладки не буде.

### Як це влаштовано

Програма не може замінити контейнер, у якому сама працює, тож поруч працює
окремий контейнер **`hlviewer_updater`**. Він має доступ до `docker.sock` і до
каталогів обох репозиторіїв і приймає команди лише від бекенда (спільний
`UPDATER_TOKEN`). Портів назовні не публікує.

Що відбувається після «Оновити»:

| Крок | Що робиться | При збої |
|---|---|---|
| 1. Підготовка | Перевірка: коміти продовжують встановлену версію, у файлах проєкту немає ручних правок, не йде оновлення даних (hostlib), вистачає місця для копії бази | «Не виконано», нічого не змінено |
| 2. Збирання образів | Образ фронтенда — завжди, бекенда — лише якщо змінилися `requirements.txt`/`Dockerfile` (код бекенда підключено з диска). Стара версія працює | «Не виконано» |
| 3. Копія бази | Планувальник зупиняється, `pg_dump` → `backups/pre-update-<дата>.dump` (зберігаються 5 останніх) | «Не виконано», планувальник запускається знову |
| 4. Перемикання | `git merge --ff-only` в обох репозиторіях, перестворення `fastapi_v2` (на старті він виконує `alembic upgrade head`) | відкат |
| 5. Перевірка | Бекенд відповідає на `/config` (до 240 с), ревізія бази = head нового коду, потім планувальник і фронтенд | відкат |

**Відкат:** контейнери зупиняються; якщо міграції змінили базу — `alembic downgrade`
до попередньої ревізії (новим кодом, у якому є ці downgrade), а якщо він не вдався —
відновлення з копії; потім `git reset --hard` на попередні коміти, повернення
попередніх образів (`:prev`) і запуск. Підсумок — «Повернено попередню»; якщо не
піднялась і попередня версія — «Збій» (копія бази лишається в `backups/`).

**Прибирання:** після успішного оновлення й після відкату — `docker image prune -f`
(лише образи без тегу, тобто старі версії) і `docker builder prune -f --filter until=168h`
(кеш збирання, старший за тиждень). `docker system prune` і `image prune -a` не
виконуються: вони прибрали б образ `:prev`, до якого робиться відкат, і чуже на цьому хості.

> Дані, що їх програма записала між копією бази та відкатом із відновленням,
> втрачаються — це хвилини, і планувальник у цей час зупинено. Відновлення з копії
> використовується лише тоді, коли downgrade неможливий.

### Увімкнення (один раз)

1. Дописати в `.env`:

   ```env
   COMPOSE_PROFILES=updater
   UPDATER_ENABLED=true
   # openssl rand -hex 32
   UPDATER_TOKEN=ЗАМІНИТИ
   # Каталог, у якому лежать HLViewer і hl_frontend (як у розділі 2)
   HLV_ROOT=/opt/hlviewer
   ```

2. Підняти стек — бекенд перечитає `.env`, updater збереться й запуститься:

   ```bash
   cd /opt/hlviewer/HLViewer
   docker compose up -d --build
   docker compose ps          # hlviewer_updater — Up, fastapi_app_v2 — healthy
   ```

3. В адмінці «Версія програми» → «Перевірити оновлення». Адреси репозиторіїв і
   гілки (`master` / `main`) підставляються з `git remote` самих репозиторіїв;
   змінити — блок «Репозиторій». Для приватного репозиторію потрібен
   fine-grained токен GitHub з правом **Contents: read-only** на обидва
   репозиторії; він зберігається в `update/config.json` (права 600) і в інтерфейсі
   не показується.

### Що блокує оновлення

- **Ручні правки у файлах проєкту** (`git status` показує змінені файли) — їх
  треба закомітити в GitHub або скасувати: `git checkout -- <файл>`. `.env`,
  `logs/`, `hostlibs/` тощо не враховуються — вони в `.gitignore`.
- **Власні коміти на сервері**, яких немає в GitHub — оновлення лише
  перемотує вперед і нічого не переписує.
- **Оновлення даних (hostlib) у процесі** — дочекатися завершення.

### Чого updater не робить

- **Не оновлює сам себе.** Якщо змінився код у `updater/`, вкладка про це
  попередить; після оновлення: `docker compose up -d --build updater`.
- **Не запускає нові сервіси**, додані в `docker-compose.yml`, — після такого
  оновлення виконайте `docker compose up -d`.

### Де дивитися

- Журнал кожного оновлення — кнопка «Журнал» в історії на вкладці; файли —
  `update/jobs/*.json`.
- Логи контейнера: `docker compose logs -f updater`.
- Копії бази: `backups/pre-update-*.dump`. Відновлення вручну:

  ```bash
  docker compose stop fastapi_v2 scheduler_v2
  docker exec -i postgres_db_v2 sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner --single-transaction' \
    < backups/pre-update-20261028-120000.dump
  docker compose up -d
  ```
