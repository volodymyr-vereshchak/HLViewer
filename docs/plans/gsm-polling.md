> вердикт по драйверам — в разделе «Агент опроса».
>
> Составлен 04.09.2026 на коде `456f9bb`. Все ссылки вида `файл.py:123`
> действительны на этот коммит — перед реализацией их стоит перепроверить.
> Источник фактов об Ask2 — декомпиляция `Ask2.exe`, `Devices\cask2.dll`
> и драйверов через ilspycmd; ничего в папку Ask2-218 не писалось.
> Реализация не начата: код по этому плану ещё не написан.

## Context

Сейчас данные приборов попадают в HLViewer **только чужими руками**: Ask2 (WPF,
.NET Framework) звонит модемом на приборы, складывает бинарные hostlib-файлы, они
пакуются в zip на сетевой шар, а `scheduler_runner` раз в 120 с замечает свежий
архив и заливает его в Postgres (`update_hostlibs` → `S*R*D/R/A/U/S.*` →
`bulk_upsert_via_copy`). То есть HLViewer — конечное звено чужого конвейера.

Задача: **перенести сам опрос внутрь HLViewer** и убрать Ask2 из контура.
Пользователь из браузера должен запускать опрос вручную и по расписанию, видеть
живой прогресс и лог, а потом разбирать историю опросов и ошибки.

Согласовано с пользователем:

| Вопрос | Решение |
|---|---|
| Канал связи | **CSD — дозвон GSM-модемом** (ATDP<номер> → CONNECT). TCP пока не нужен, но транспорт делаем сменным |
| Где крутится опросчик | **Только на клиентских машинах.** Модем в сам сервер не втыкаем — см. ниже |
| Как браузер достаёт модем на ПК | **Локальный агент** на ПК (служба/exe), сам тянет задания из API. Не Web Serial |
| График | **Поприборно** (`auto_poll` + свои часы), глобальные часы — значение по умолчанию |
| Судьба Ask2 | **Сразу заменяем**, как только наш опрос заработает |
| Парк приборов | Разнородный: Флоутек ВР-2/ВР-3/ПКВ, КПЛГ, ВЕГА, Універсал, В25 и др. |
| Что читаем за сеанс | Часовые + суточные архивы, аварии + вмешательства, мгновенные + параметры |
| Драйверы приборов | **Вариант A** — переиспользуем готовые `Devices\calc*.dll` |
| Кто запускает опрос вручную | **Любой авторизованный пользователь**; настройки — админские |

Разнородность парка — определяющий факт: пять с лишним протоколов писать с нуля
нереально, поэтому основная ставка — **переиспользовать готовые драйверы Ask2**
(`Devices\calc*.dll`), а не переписывать обмен.

### Почему модем не ставим в сервер

Рассматривался вариант «модем воткнут прямо в сервер, опрос делает бекенд».
Он отпал, и причина не в удобстве:

- **Из бекенда опросить нельзя в принципе.** `calc*.dll` — сборки .NET
  Framework; Python не загрузит их в свой процесс. Любой опрос — это
  отдельный .NET-процесс, то есть тот же агент, только на другой машине.
- **Прод есть и на Linux (Docker, `python:3.11-slim`).** .NET Framework там
  не запускается вовсе, а Mono отпадает из-за ссылок `cask2.dll` на WPF:
  `Global.GetValueResource()` вызывается из `Protocol.StartPollCommon()`, и
  падение произошло бы на JIT-компиляции метода, где внутренний `try/catch`
  его уже не поймает. То есть на Linux-проде драйверы Ask2 не работают
  никак — вариант «сервер сам звонит» существовал бы только на Windows-проде,
  и две установки одного продукта разошлись бы по возможностям.

**Решение: опрос всегда на клиентской машине.** Если нужна пропускная
способность — ставится одна выделенная Windows-машина с несколькими модемами
(скажем, пять COM-портов) и на ней тот же агент. Для схемы это обычный клиент:
пул из пяти воркеров разбирает очередь в пять линий одновременно. Ни бекенд,
ни схема БД при этом не меняются, и оба прода — Windows и Linux — работают
одинаково.

## Архитектура

Опрос **не может** жить внутри `fastapi_v2`/`scheduler_v2`: драйверы — сборки
.NET Framework, Python их не загрузит, а на Linux-проде они не работают вовсе.
Поэтому он выносится в отдельный процесс на клиентской машине — **агента
опроса**, — а бэкенд становится диспетчером очереди.

```
браузер ──HTTP(cookie)──► FastAPI ──► Postgres: poll_device (+ last_poll_at) / poll_log
                             ▲                         │
                             │ X-Agent-Key             │ задания
                             │                         ▼
                    ┌────────┴────────┐        ┌────────────────┐
                    │  АРМ Іваненко   │        │ виділена машина│
                    │  COM5 + модем   │        │ COM1..COM5     │
                    └────────┬────────┘        └───────┬────────┘
                             ▼ ATDP<номер>             ▼ ×5
                          прибор                    прибори
```

Агент — один и тот же бинарник везде; разница только в числе модемов и в том,
какие приборы за ним закреплены. Агент **сам инициирует** соединение с API
(тянет задания сам), поэтому машине не нужен ни белый IP, ни открытый порт,
ни VPN-вход внутрь — и неважно, где стоит бекенд, на Windows или в Linux-Docker.

### Никакой очереди заданий: сервер не ждёт ответов

Очередь `poll_task` (выдача заданий, захват, возврат зависших, вытеснение
устаревших) из плана убрана. Вместо неё — **состояние прибора**:

> На приборе хранится `last_poll_at` — когда его в последний раз успешно
> опросили. Расписание — часы на том же приборе. «Задание» нигде не лежит:
> оно **вычисляется** сравнением `last_poll_at` с последним наступившим слотом.

Сервер не раздаёт заданий и не ждёт ответа ни на что. Он держит справочник
приборов и отметки о последнем опросе; всё остальное решает агент:

1. агент забирает свой план — приборы, отмеченные у него, с их настройками,
   часами и `last_poll_at`;
2. по каждому сам считает: «последний слот был в 08:00, опрошен в 08:15 —
   пропускаю; этот опрошен вчера — беру»;
3. опрашивает, шлёт данные и лог, и по успеху сервер проставляет новый
   `last_poll_at`.

Что это даёт, помимо того что кода становится втрое меньше:

- **Выключенный ПК ничего не ломает и ничего не копит.** Не бывает
  «зависших заданий», которые надо возвращать в очередь, и не бывает
  накопившихся за неделю дублей: невыполненное не остаётся заданием,
  оно остаётся фактом «прибор давно не опрошен».
- **Подстраховка одного оператора другим получается сама.** Если у Іваненка
  ПК выключен, а те же приборы отмечены и у Петренка — его агент видит по
  `last_poll_at`, что они не опрошены, и берёт их. Ничего специально
  «переназначать» не нужно.
- **Пропущенный слот не теряется.** Прибор, не опрошенный в 08:00, остаётся
  «просроченным» и будет опрошен, как только появится живой агент.

Цена — сервер знает о происходящем ровно то, что ему рассказали агенты
(телеметрия), и не может отличить «прибор сейчас опрашивается» от «никто
не взялся», кроме как по этой телеметрии. Для наших целей этого достаточно,
а взамен исчезает целый слой согласования.

## Схема БД (новая миграция, `down_revision = "d1f3a5c7e9b2"`)

Ревизию выбрать в принятом здесь стиле (рукописный hex-подобный id, напр.
`e2a4c6b8d0f3`), не автогенерацией.

### `poll_agent` — кто может опрашивать

| колонка | тип | смысл |
|---|---|---|
| `id` | BigInt PK | |
| `name` | varchar(100) uq | «АРМ Іваненко», «Опитувальна ЗЛВУМГ» |
| `kind` | varchar(8) | `workstation` \| `dedicated` — только для отображения |
| `key_hash` | varchar(255) | ключ показывается один раз при создании, хранится хэш |
| `branch_id` | FK→grmu_branch SET NULL | область ответственности |
| `active` | bool | |
| `last_seen_at`, `version`, `host` | | самоописание из `hello` |

**Граница ответственности.** Сервер отдаёт агенту список заданий с данными
приборов — и на этом его роль заканчивается. Сколько на машине модемов, на
каких портах, в каком порядке их занимать и что делать, когда все заняты, —
целиком дело службы на этой машине. Она же строит свою очередь и заливает
результат обратно.

Поэтому в схеме нет ни `poll_device.com_port`, ни списка портов у агента, ни
счётчиков занятости модемов: серверу нечего с ними делать, а лишнее знание
означало бы лишний код по обе стороны.

`baud` остаётся на приборе: скорость определяет прибор на том конце линии,
это не свойство машины. `tcp_host`/`tcp_port` — тоже на приборе, сетевой адрес
принадлежит прибору, а не звонящему.

### `poll_device` — как дозвониться до прибора

Это карточка **корректора**, а не линии. Корректоры в базе живут в трёх видах,
поэтому `poll_device` ссылается ровно на один из трёх (CHECK «заполнено ровно
одно» — приём уже применён в `virtual_line_member`):

| ссылка | что это | куда лягут данные |
|---|---|---|
| `gas_volume_calc_id` | прибор ЛУМГ из `ASK.CFG` | `hourly/daily/sys/edit_archive`, `params` |
| `dpd_line_id` | линия ДПД (текущий корректор берётся из истории `dpd_line_device`) | `dpd_line_hourly/daily_archive` |
| `dpd_device_id` | корректор промышленности (`ser_num + corector_type + ch_num`) | `dpd_hourly/daily_archive`, точка учёта разрешается через окна `enterprise_device` |

Смысл третьей строки — требование пользователя: **промышленность, которая
сейчас тянется через ДПД API, должна опрашиваться и напрямую по GSM.** Якорь
именно `dpd_device`, а не `enterprise`: корректор переезжает между точками, и
архив в этой части базы ключуется прибором (см. `enterprise_device.removed_at`).

⚠️ **Открытый вопрос — маппинг значений для целей ДПД.** `dpd_daily_archive`
хранит `dvst_alwrk`/`dvwrk_alwrk` (стандартный и рабочий объём), а `GasData`
из драйвера несёт `V`/`Vru`. Соответствие выглядит очевидным, но проверять его
надо на реальном приборе, сверив GSM-опрос с тем, что за те же сутки отдал ДПД
API. Кроме того `dpd_line_*` и `dpd_*` архивы хранят только объём, давление и
температуру — аварии, вмешательства и параметры, которые GSM-опрос принесёт,
класть в этой ветке некуда. Поэтому очередь работ: **сначала цели
`gas_volume_calc`, ветки ДПД — вторым этапом, после сверки.**

Остальные поля — калька с `ask2cfg.xml`, чтобы миграция настроек была
механической:

`enabled` · `auto_poll` · `poll_times` ·
`channel` (`com`/`tcp`) · `is_modem` · `phone` · `init_str` (деф. `AT&F`) ·
`dial_prefix` (деф. `ATDP`) · `baud` (9600) · `tcp_host`/`tcp_port` ·
`protocol_id` (деф. из `gas_vol_calc_type.type_id`) · `device_address` (деф. из
`gas_volume_calc.address`) · `access_code` · `access_password` ·
`answer_timeout_sec` (7) · `pause_between_ms` (400) · `repeat_count` (3) ·
`preamble_count` (0) · `depth_days` · `priority` (int) · `note`

Модемные и адаптерные поля — точная калька `cask2.Devices.COMChannel`
(подтверждено декомпиляцией): `modem_connect_timeout_sec` (40),
`modem_repeat_call_count` (3), `modem_pause_after_connect_ms` (400),
`is_adapter` · `adapter_line` · `adapter_speed` · `adapter_level_in` ·
`adapter_level_out` · `adapter_is_frequency` · `adapter_is_radio`.
Адаптер/радиоканал сейчас не задействован, но колонки заводим сразу —
иначе перенос настроек из Ask2 будет не механическим, а выборочным.

`access_password` — **plaintext-колонка, как `grmu_branch_dpd_credential.password`**,
и по тому же правилу: GET её никогда не отдаёт, PUT с пропущенным полем не
затирает. Шифрования в проекте нет, вводить его здесь — отдельная задача.

**Расписание — на приборе.** `auto_poll` (bool) отвечает на «опрашивать ли его
автоматически вообще», `poll_times` — свои часы этого прибора (список `HH:MM`,
NULL = взять глобальные из `poll_settings`). Глобальные часы остаются, но
становятся значением по умолчанию, а не единственным вариантом: обычный режим
— 1–2 раза в сутки, но конкретный прибор можно гонять чаще или в своё окно.

### `poll_agent_device` — кто какие приборы опрашивает

Замена прежнего `poll_device.agent_id`: связь **многие-ко-многим**
(`agent_id`, `poll_device_id`, PK по паре, обе FK CASCADE).

Так это работает у пользователя: на ПК обычно один модем на один порт, а
операторов с модемами несколько. Бэкенд спускает вниз список приборов, а каждый
агент в своих настройках отмечает галочками, какие из них берёт на себя — может
все, а может половину, поделившись с коллегой. Договариваются операторы между
собой, админ в это не вмешивается.

Отсюда два правила, оба обязательны:

- **Прибор, не отмеченный никем, не опрашивается вообще.** Это тихая потеря
  данных, поэтому в админке нужен явный индикатор «ничей».
- **Отмеченный у двоих** опрашивается тем, кто первым до него дошёл; второй
  видит уже обновившийся `last_poll_at` и пропускает. Защита от одновременного
  старта — мягкий захват прибора, см. ниже.

### Состояние опроса — на самом приборе

Вместо очереди и истории прогонов — несколько колонок на `poll_device`:

| колонка | смысл |
|---|---|
| `last_poll_at` | когда прибор **успешно** опрошен. Единственное, по чему считается «сделано» |
| `last_attempt_at` | когда была последняя попытка, успешная или нет |
| `last_status` | `ok` / `error` |
| `last_error_code` | `no_carrier` / `busy` / `no_dialtone` / `no_answer` / `timeout` / `crc` / `auth` / … |
| `last_error_text` | текст последней ошибки |
| `last_agent_id` | кто опрашивал последним |
| `last_rows` | JSONB: сколько строк по каждому архиву принёс последний опрос |
| `last_duration_ms`, `last_connect_ms` | длительность сеанса и дозвона |
| `manual_requested_at`, `manual_requested_by` | заявка на внеочередной опрос |
| `polling_agent_id`, `polling_since` | мягкий захват на время сеанса |

**Мягкий захват** нужен ровно для одного случая: прибор отмечен у двух
операторов, оба агента одновременно решили, что он просрочен. Захват — та же
атомарная UPDATE, что уже применяется в проекте, только по одной строке:

```sql
UPDATE poll_device SET polling_agent_id = :a, polling_since = now()
WHERE id = :d
  AND (polling_since IS NULL OR polling_since < now() - interval '20 minutes')
RETURNING id
```

Не вернулось ничего — прибор уже кто-то взял, агент идёт дальше. Просроченный
захват (агента выключили посреди сеанса) отпускается сам через 20 минут.
Это единственная синхронизация между агентами во всей схеме.

### `poll_log` — только последний сеанс по каждому прибору

- `poll_device_id` FK CASCADE, `ts`, `level`, `message`, `seq`.
- В начале нового сеанса строки этого прибора удаляются: интересен только
  текущий/последний лог, старые не хранятся.
- Индекс `(poll_device_id, seq)` — по нему живой лог читается инкрементально.

⚠️ **Тут есть противоречие с более ранним требованием**, и его лучше решить
сознательно. Изначально просили «историю опросов, чтобы выявить ошибки»;
хранение только последнего лога отвечает на вопрос «что было сейчас», но не
на «этот прибор всю неделю не берёт трубку по ночам».

Компромисс, который я предлагаю (дёшево и не спорит с «старые логи не нужны»):
полный текст лога хранить только за последний сеанс, **как и просили**, а
рядом вести `poll_attempt` — по одной короткой строке на попытку:
`poll_device_id`, `started_at`, `finished_at`, `status`, `error_code`,
`rows` (JSONB), `agent_id`. Это единицы сотен строк в сутки на весь парк,
ретенция 60–90 дней, зато отчёт «кто и как часто не отвечает» остаётся
возможным. Если не нужно — таблица просто не заводится, остальное не меняется.

Модели SQLModel обязательны **и** миграция: тесты строят схему из
`SQLModel.metadata`, а прод — из Alembic, и дрейф CI не ловит.

## Бэкенд

### Эндпоинты для UI (cookie-auth, мутации автоматически admin-only)

```
GET/PUT/DELETE /polling/devices/{calc_id}   настройки прибора
GET            /polling/devices/             список: настройки + last_poll_at + просрочка
POST           /polling/devices/{id}/poll    заявка на внеочередной опрос → 202
GET/POST/DELETE /polling/agents/             реестр агентов (ключ отдаётся один раз)
GET/PUT        /polling/schedule             глобальные часы по умолчанию
GET            /polling/live                 состояние всех агентов + что опрашивается
GET            /polling/live/stream          то же потоком (NDJSON)
GET            /polling/devices/{id}/log     лог последнего сеанса прибора
GET            /polling/overdue              просроченные приборы и приборы без агента
```

Средний слой авторизации (`api/main.py:261-324`) делает **любой** POST
admin-only, а admin-only GET включается подстрокой в `_ADMIN_PATH_MARKERS`.
**Решено: запускать опрос вправе любой авторизованный пользователь**, настройки
приборов и агентов остаются админскими. Значит:

- `"polling/devices"`, `"polling/agents"` — добавить в `_ADMIN_PATH_MARKERS`,
  но `GET /polling/devices/` и `/polling/live` вывести из-под этого правила:
  смотреть должны все;
- `POST /polling/devices/{id}/poll` — явное исключение из admin-only
  (новый набор `_USER_WRITE_PATHS` рядом с `_PUBLIC_PATHS`, с сохранением
  проверки сессии: исключение из «нужен админ», а не из «нужен вход»).
  Отдельным тестом закрепить, что viewer может заказать опрос, но получает
  403 на `PUT /polling/devices/{id}`.

### Эндпоинты для агента (заголовок `X-Agent-Key`, не cookie)

```
GET  /polling/agent/plan                    свои приборы: конфиг, часы, last_poll_at, заявки
PUT  /polling/agent/devices                 сохранить свой набор приборов (список id)
POST /polling/agent/state                   телеметрия: версия, хост, что сейчас, очередь
POST /polling/agent/devices/{id}/start      мягкий захват прибора на время сеанса
POST /polling/agent/devices/{id}/log        строки лога (первая партия чистит старый)
POST /polling/agent/devices/{id}/data       разобранные записи
POST /polling/agent/devices/{id}/finish     итог: ok/error, error_code, счётчики
```

Весь протокол — семь вызовов, и ни одного, где сервер чего-то ждёт.

**`GET /polling/agent/plan`** — сердце схемы. Отдаёт по каждому прибору агента:
полную конфигурацию связи, часы опроса (`auto_poll`, `poll_times`, иначе
глобальные), `last_poll_at`, признак заявки на ручной опрос, последние даты по
архивам для инкрементальной дочитки — **и текущее время сервера**.

Серверное время здесь не украшение: часы на АРМ уходят, а решение «слот
наступил» принимает агент. Он берёт смещение из ответа и считает по нему,
а не по своим часам. Без этого ПК с убежавшими на час часами будет либо
опрашивать зря, либо пропускать слот.

Ответ снабжается `ETag`: план меняется редко, а тянуть его агент будет раз в
10–15 секунд.

**`PUT /polling/agent/devices`** — набор приборов, отмеченный оператором в окне
настроек. Хранится в `poll_agent_device` на сервере, а не локально: иначе не
показать в админке приборы-сироты и не понять, кто чем занят.

**`POST /polling/agent/state`** — телеметрия для окна наблюдения: что
опрашивается сейчас, что осталось в локальной очереди агента, номер последней
отправленной строки лога. Раз в 10–15 секунд. Это же и признак жизни: по
`last_seen_at` фронт решает, что связь потеряна.

Эти пути надо вывести из cookie-миддлвары (по образцу `_PUBLIC_PATHS`) и
закрыть проверкой ключа агента — иначе default-deny вернёт 403 на каждый POST.

### Как агент решает, что опрашивать

Никакого захвата заданий — есть план и арифметика по нему. Для каждого прибора
из плана агент считает:

```
слот = последний наступивший час из poll_times (или глобальных),
       по времени сервера
если manual_requested_at задан и позже last_poll_at  -> опросить вне очереди
иначе если not auto_poll                             -> пропустить
иначе если last_poll_at >= слот                      -> пропустить, уже сделано
иначе                                                -> опросить
```

Пример из жизни: слоты 08:00 и 16:00, на часах 12:00, `last_poll_at = 08:15`.
Последний наступивший слот — 08:00, опрос был позже него, значит прибор
опрошен, ничего не делаем. В 16:05 последний слот уже 16:00, `08:15 < 16:00` —
опрашиваем.

Тот же расчёт даёт и подстраховку: если ПК Іваненка выключили и в 08:00 никто
не позвонил, то в 09:00 агент Петренка (у которого те же приборы отмечены)
увидит `last_poll_at` вчерашним, то есть меньше слота 08:00, — и опросит.
Ничего переназначать не нужно, просроченность видна прямо из данных.

Перед сеансом — мягкий захват (`POST …/devices/{id}/start`); не удался, значит
кто-то уже звонит, пропускаем. После успеха сервер проставляет `last_poll_at`,
и второй агент, дойдя до этого прибора, увидит его уже опрошенным.

Ручная заявка обрабатывается **вне очереди**: агент ставит её в голову своей
локальной очереди, не дожидаясь конца планового обхода.

### Что где хранится и что считается опрошенным

**На сервере** — справочник приборов, их настройки, `last_poll_at` и итог
последней попытки, набор приборов каждого агента, лог последнего сеанса.
Заданий нет: их просто не существует как сущности.

**У агента** — только его собственная очередь на текущий обход, в оперативной
памяти. На диске `agent.json` и свой лог; машину можно переустановить, ничего
не потеряв. Перезапуск агента не требует никакой уборки на сервере: он заново
тянет план и заново считает, что просрочено. (В варианте с очередью здесь
нужна была отдельная процедура «сдать всё, что за мной числилось» — теперь
она не нужна вовсе.)

Единственное, что подчищается, — зависший мягкий захват, и он отпускается сам
по таймауту.

**«Что уже опрошено» ведётся в двух местах, и они не дублируют друг друга:**

1. **Факт опроса** — `poll_device.last_poll_at`. По нему считается расписание
   и строится отчёт о просрочке.
2. **Какие данные есть** — сами архивные таблицы. Глубина дочитки берётся
   запросом `MAX(period)` по каждому архиву линии и уезжает в ответе `plan`;
   драйвер получает её через заглушку `IPollDataService` и читает «с этого
   места и дальше».

Соблазн завести таблицу покрытия велик — у ДПД такая есть
(`dpd_device_coverage`). Но там она появилась ради дочитки **в прошлое** через
платный API; здесь чтение всегда идёт вперёд от последней записи, и отдельный
учёт только разошёлся бы с фактическим содержимым архива.

Повторный опрос того же периода безопасен: `bulk_upsert_via_copy` с уникальным
констрейнтом просто ничего не вставит. Даже если два агента почему-то опросят
прибор одновременно, дублей в архиве не будет.

### Приём данных — прямо в DAO, без файлов

Агент отдаёт разобранные записи; бэкенд кладёт их существующими средствами:

```python
calc = await GasVolumeCalcDao(session).get_or_create(address=addr, lumg_id=lumg_id)
line = await LineDao(session).get_or_create(gas_volume_calc_id=calc.id, line=line_no)
await HourlyArchiveDao(session).bulk_upsert_via_copy(rows, HOURLY_ARCHIVE_CONSTRAINT)
# то же для daily / sys / edit / params
```

Альтернатива — писать hostlib-файлы и звать `update_direct()`. Отвергнута:
это лишний круг «сериализация → zip → распаковка → десериализация» ради тех же
самых DAO, плюс наследуется лимит имени файла (адрес — 3 цифры, линия — 1).
Идемпотентность даёт тот же уникальный констрейнт, что и при заливке из zip,
поэтому повторный опрос того же периода безопасен.

### Расписание: шедулер тут не нужен

Это, пожалуй, самое приятное следствие. Расписание — просто данные:
`auto_poll` и `poll_times` на приборе, глобальные часы как значение по
умолчанию. Их читает агент и сам решает, наступил ли слот.

Значит **в `scheduler_runner` не появляется ничего**: ни `maybe_poll_devices()`,
ни постановки заданий, ни отдельного тика. Правка расписания в админке
подхватывается за 10–15 секунд — ровно за то время, через которое агент
перечитает план.

Единственная фоновая работа на сервере — уборка, и она мелкая: отпустить
мягкие захваты старше 20 минут (это может делать и сам эндпоинт захвата,
не заводя фоновой задачи) и подрезать `poll_attempt` по ретенции, если эту
таблицу заводим.

Пропущенный слот при этом не теряется и не дублируется — в отличие от очереди,
где для этого понадобились `slot_at`, частичный уникальный индекс и вытеснение
`superseded`. Здесь просроченность просто следует из `last_poll_at < слот`.

### Стриминг прогресса

Повторяем `/enterprise/volumes/stream`: `StreamingResponse`,
`media_type="application/x-ndjson"`, `X-Accel-Buffering: no`, ping раз в 15 с,
последнее-значение для `progress` и очередь для редких событий.

Два обязательных довеска, иначе «живой лог» не поедет:
1. `StreamAwareGZipMiddleware` (`api/main.py:218-232`) сейчас исключает **один

2. nginx: `location /api/polling/` с `proxy_read_timeout 600s` — иначе дефолтные
   60 с рвут поток.

К словарю событий стрима (`progress` / `status` / `ping` / `result` / `error`)
добавляется **`log`** — строка с прибором, уровнем и текстом.

### Что показала декомпиляция

Разобраны `Ask2.exe`, `Devices\cask2.dll` (ядро), `calcFloutek.dll`,
`calcFloutecBP2.dll`, `CalcPKV.dll`, `calcKPLG.dll`, `CalcVega.dll`,
`calcUniversal.dll`, `libModels.dll`, `_licdrv.dll` (ilspycmd, вывод — только
в скретчпад сессии, в папку Ask2-218 ничего не писалось).

**1. Все драйверы — managed .NET Framework 4.0, плагины MEF.**
Каждая `calc*.dll` содержит `[Export(typeof(IDeviceRegister))] class RegCalcDev`
с методом `Register()`, который добавляет описание прибора в `Global.CalcsSource`
и экземпляры протоколов в `Global.Protocols`. Сами протоколы помечены
`[Export(typeof(Protocol))]`. Никакого нативного кода, никакого COM.

**2. Контракт драйвера — базовый класс `cask2.Devices.Protocol`** (в `cask2.dll`),
а не интерфейс. Виртуальные методы, которые переопределяет драйвер:

```
Init()
PollDayImplementation()        PollHourImplementation()     PollInstantImplementation()
PollPeriodicalImplementation() PollStatImplementation()     PollAlarmImplementation()
PollAuditImplementation()      PollBezopImplementation()    PollDailyAlarmsImplementation()
PollCalibrImplementation()     CorrectTimeImplementation()  ContractHourImplementation(byte)
WriteFHPImplementation(Passport)
Alarm(...) / Audit(...) / Bezop(...)   ← расшифровка кодов событий в текст
PollSessionBeginImplementation() / PollSessionEndImplementation()  ← только UId 42 и 5
```

**3. Как хост запускает драйвер** (`Ask2.Code.Poll.PollEngine.COMPortTread`):

```csharp
var proto  = Global.Protocols.Find(x => x.Id == device.ProtocolID);
var driver = (Protocol)Activator.CreateInstance(proto.GetType());
driver.dataStore = <реализация IPollDataService>;   // у Ask2 — WCF-клиент
driver.QItem     = queueItem;
driver.StartPoll(serialPort);                        // порт открыт и уже дозвонен
```

Четыре строчки — весь интеграционный шов. `StartPoll` внутри гоняет фиксированную
последовательность: WriteFHP → StatParam → Instant → Hour → Day → Periodical →
Alarm → DailyAlarms → Audit → Bezop → Calibrate → CorrectTime → ContractHour,
с `CheckBreak()` между шагами (там же логируется «No Carrier Detect» по падению
`serialPort.CDHolding`).

**4. Вся связь драйвера с БД — один интерфейс `IPollDataService`.**
Он большой (≈250 методов, WCF `[ServiceContract]`), но драйвер Флоутека трогает
девять: `LastRecordStatParm` ×2, `SaveStatParam`, `SaveGasPeriodical`,
`SaveGasInstant`, `SaveGasHour`, `SaveGasDay`, `SaveCalc`, `SaveAudit`,
`SaveAlarm`; плюс базовый класс зовёт `LastDateGasHour/Day/Instant/Alarm/Audit/
StatParm/Periodical`. Остальное — `throw new NotImplementedException()`.
**Это и есть точка врезки:** агент реализует `IPollDataService` как локальную
заглушку, копит записи в памяти и отправляет их нашим `POST …/data`.

**5. Глубина дочитки достаётся бесплатно.** Драйвер не решает сам, с какой даты
читать: он спрашивает `dataStore.LastDateGasHour(lineId)`, и если ответ старше
двух месяцев — сам ограничивает начало первым числом прошлого месяца; при
`QItem.IsPeriod == true` берёт явные `BeginPeriodDT/EndPeriodDT`. Значит наша
заглушка отвечает по данным HLViewer, и инкрементальный опрос работает без
единой строчки дополнительной логики. За период — то же самое через `IsPeriod`.

**6. Лицензии в драйверах нет.** `licAsk2.lic` читается ровно в одном месте —
`Ask2.Wnd.UserLogin.IsRegistrApp()`: десериализация `FileLic`, `ListUIdDevice`,
сверка `MachineName`/`UserDomainName`/`DateValid`. `_licdrv.dll` — это серийник
матплаты (`Win32_BaseBoard`) для `LicLoc.exe`. Внутри `calc*.dll` нет ни одной
ссылки на лицензию. Технически агент, грузящий эти DLL, проверки не встречает.
⚠️ Но это вопрос **юридический, а не технический**: DLL принадлежат
ДП «Укргазтех», и использовать их вне Ask2 нужно с их согласия. Решение —
за пользователем; технический план от него не зависит (см. запасной вариант C).

**7. WPF не мешает.** `cask2.dll` ссылается на `PresentationCore`/`WindowsBase`,
и `Global.GetValueResource()` читает `Application.Current.Resources`, но обёрнут
в `try/catch` и при отсутствии приложения возвращает `""`. То есть консольный
агент работает, просто тексты логов пустые. Лечится дёшево: создать `Application`
в STA-потоке и подгрузить `Resources/lang.*.xaml` — и логи снова человеческие.

### Насколько драйверы однородны и как их типы ложатся на нашу базу

Проверено по коду, три разных ответа.

**Поля данных — да, единый формат.** Все драйверы заполняют одни и те же классы
`cask2.Models.Data`: `GasData` (архивы и мгновенные), `EventData` (аварии и
вмешательства), `StatData` (параметры), `Passport`. `GasData` заметно богаче
наших таблиц (энергия, `V0/Q0/Vday0`, единицы, стандарты температуры), мы
кладём подмножество — ровно то, что и сейчас приходит в hostlib:

| hostlib `THostRecR` (29 Б) | наш `HourStruct` | колонка |
|---|---|---|
| `vH` | `volume` | `hourly_archive.volume` |
| `e` (`THostDataExt`, флаги) | `unknown` | не пишется |
| `dP` | `w_volume_dp` | `hourly_archive.w_volume_dp` |
| `p` / `t` / `ro` | `pressure`/`temperature`/`density` | одноимённые |

Поле `e` — не мусор: биты `0x40`/`0x20` это признаки «в записи была авария /
вмешательство», и читаются они **только** для протоколов 1000, 1020, 1060,
1070, 1075, 1077 (`ConvertHostlib.ConvertStructHourToGasData`). Там же
подтверждается уже сделанное на фронте: `dP` для счётчиковых линий несёт `Vru`,
а не перепад — отсюда «Макс./Мін. витрата» вместо «дельтаП».

**Коды аварий — нет, они свои у каждого семейства.** `EventData` несёт голый
`Code` плюс `ProtocolID`, а расшифровывает его драйвер: `FloutekAUparsing`
(~338 ветвей), `KplgAUparsing` (~284), `PKVAUparsing`, `UniAUparsing`. ВЕГА и
ВР-2 своего парсера не имеют: ВР-2 переиспользует `FloutekAUparsing`, то есть
у семейства Флоутек таблица общая.

Для нас это уже решено и ничего не ломает: `sys_type` и `edit_type` в нашей базе
ключуются парой `(код, gas_volume_calc_type_id)`, то есть словарь и так свой на
каждый тип прибора. На 04.09.2026 в базе разработки заполнено 9 типов —
от 215 до 1117 кодов аварий и 104–128 кодов вмешательств на тип. Агент отдаёт
сырой код, текст рисует существующий словарь, как и сегодня.

**Типы корректоров — не совпадают напрямую, нужна таблица перевода.**
Наш `gas_vol_calc_type.type_id` — это порядковый номер перечисления
`ConvertCFGtoXLS.Enum.TypeCalc` из `ConvertCFG.dll` (то есть код типа в
`ASK.CFG`), а не `ProtocolID` драйвера. Сверено поимённо: 9 = ФлоІнек,
29 = Флоутек-ТМ 3.4, 33 = Флоутек-ТМ ГОСТ586, 43 = КПЛГ, 47 = Флоутек ВР2,
49 = Данифлоу 7, 56 = Флоутек ПК-В.

Перевод делается в два шага, оба есть в коде Ask2:
`ConvertUId.GetUIdCalc(type_id)` → `UId` прибора, затем `UId` → протоколы,
которые зарегистрировал драйвер (`RegCalcDev.Register`).

| наш `type_id` | прибор | `UId` | протоколы |
|---|---|---|---|
| 5, 33 | Флоутек / Флоутек-ТМ ГОСТ586 | 33 | 999, 1000 |
| 9, 34 | ФлоІнек | 30 | — |
| 6, 35 | Флоукор | 20 | — |
| 29 | Флоутек-ТМ 3.4 | 60 | — |
| 47 | Флоутек ВР2 | 70 | 1070, 1071 |
| 48, 49 | Данифлоу СОУ112 / 7 | 42 | — |
| 56 | Флоутек ПК-В | 77 | 1077, 1078 |
| 0–4, 13–16, 27–28, 30–31 | семейство SF | 10 | — |
| 8 / 10, 36 / 40 | УТГ-1 / ПМ-3В / Данифлоу | 50 / 75 / 40 | — |

Две оговорки, обе важны для шага импорта:

1. **`type_id` не определяет протокол однозначно** — у одного `UId` их два
   (999/1000 у ВР-1, 1070/1071 у ВР-2, 1077/1078 у ПК-В: «РД» против «в.37»,
   обычный против «E_kWh», обычный против «споживач»). Поэтому `protocol_id`
   и хранится **на приборе**, а импорт может лишь подставить вариант по
   умолчанию — окончательный выбирает человек, как и в Ask2.
2. **Таблица `ConvertUId` в имеющейся у нас `ConvertCFG.dll` устарела.**
   В ней нет ни 43 (КПЛГ), ни наших 59 (Флоутек ВР2 2020) и 61 (Данифлоу
   вер.8) — на них она возвращает 255 («неизвестно»). Эти три строки надо
   доопределить руками (или взять более свежую `ConvertCFG.dll`) и закрыть
   тестом: **у каждого типа в `gas_vol_calc_type` должен быть протокол**.

```
DiscardIn/Out; RTS=0; 50ms; DTR=0; 500ms
ReadTimeout=1000, WriteTimeout=500; DTR=1; 1000ms; RTS=1; 50ms
→ "ATE0V1\r"        500ms, ответ прочитать и выбросить
→ ModemInitStr+"\r" (деф. "at&f"), ReadTimeout=2000, ждать 2 с, искать "OK"
ReadTimeout = AnswerTimeOut*1000; сброс буферов
номер: если len>3 и не начинается с "atd" — приписать "atd"
→ "<номер>\r";  ReadTimeout = ModemConnectTimeOut*1000 (деф. 40 с)
цикл по 200 мс до таймаута, накапливая ответ:
    "CONNECT"/"CARRIER" + цифры → успех (цифры = согласованная скорость)
    иначе искать: NO CARRIER | BUSY | ERROR | NO DIALTONE | NO ANSWER | RING
    плюс аппаратный признак port.CDHolding
успех   → RTS=1, порт отдаётся драйверу
неуспех → DTR toggle, "+++\r", 500ms, "ATH0\r", следующая попытка
конец сеанса → 1.1 c, сброс буферов, DTR toggle, "+++", 1.2 c, "ATH0\r", 1.2 c, читать ответ
```

Отсюда прямо выводится словарь `poll_device.last_error_code`: `no_carrier`, `busy`,
`no_dialtone`, `no_answer`, `modem_error`, `connect_timeout`, `port_busy`,
плюс протокольные `crc`, `auth`, `timeout`.

### Один модем — один прибор

В парке пользователя за каждым прибором стоит свой модем со своим номером,
поэтому **задание = прибор = один дозвон**, и группировать нечего.

Ask2 группировку умеет — поток COM-порта берёт задание и подтягивает все
остальные с тем же `ModemCallNumberPhone` и портом, отрабатывая их за один
звонок. Мы это не воспроизводим: лишний код ради случая, которого нет.
Схема к нему готова (`phone` лежит на приборе), так что если появится объект
с несколькими приборами за одним модемом — группировка добавляется
надстройкой, ничего не ломая.

**Следствие, которое надо считать заранее:** время опроса всего парка =
(число приборов ÷ число агентов) × (дозвон + сеанс). При ~2–4 минутах на
прибор один модем вытягивает 15–30 приборов в час. Если парк больше окна —
это решается не кодом, а вторым модемом и вторым агентом; приоритеты в очереди
задают, кто важнее, если окно всё же не закрылось.

### Что это добавляет к схеме БД

К `poll_device` — недостающие поля из `COMChannel`:
`modem_connect_timeout_sec` (40), `modem_repeat_call_count` (3),
`modem_pause_after_connect_ms` (400), `priority` (int),
`is_adapter` + `adapter_line`/`adapter_speed`/`adapter_level_in`/`adapter_level_out`/
`adapter_is_frequency`/`adapter_is_radio` (у Ask2 есть режим адаптера/радиоканала —
заводим колонки сразу, чтобы миграция настроек была механической).

Ответ `plan` несёт, помимо конфигурации прибора, **последние даты по каждому
типу архива** — их агент отдаёт драйверу через заглушку `IPollDataService`,
не делая отдельного round-trip'а на каждый `LastDate*`.

### Устройство агента

Проект `agent/` — консольное приложение .NET Framework 4.8 (net48 грузит net40
без плясок), устанавливается службой. Бинарник один и тот же и на рабочем месте
оператора, и на выделенной опросной машине с пятью модемами: различаются только
`agent.json` и набор закреплённых приборов.

```
HlvAgent.exe
├─ ApiClient           HTTP: plan / state / start / log / data / finish (X-Agent-Key)
├─ ModemDialer         восстановленная последовательность выше
├─ DriverHost          MEF-композиция папки Devices\, Global.Protocols,
│                      Activator.CreateInstance, StartPoll(serialPort)
├─ CollectingStore : IPollDataService     ← ядро врезки: Save* копит, LastDate* отвечает
├─ ModemPool           модемы этой машины: один поток-воркер на модем
└─ SettingsForm        --settings: модемы + список приборов галочками (WinForms)
```

### Цикл работы и пул модемов

Всё, что ниже, — внутреннее дело агента; сервер об этом не знает.

```
раз в 10–15 с:
    plan  = GET /polling/agent/plan          (ETag, обычно 304)
    due   = [прибор из plan, если просрочен или заказан вручную]
    очередь := ручные заявки, затем остальные по приоритету
    state = POST /polling/agent/state        (что делаю, что осталось)

каждый воркер модема, освободившись:
    взять следующий прибор из очереди
    start → не удалось (кто-то уже звонит) → пропустить
    дозвон → драйвер → log/data по ходу → finish
```

Модемов на машине один (обычный случай) или несколько; **на каждый модем —
свой воркер**. Заняты все — приборы ждут в локальной очереди. Никакой
диспетчеризации писать не нужно: очередь плюс воркеры и есть всё поведение.

Отсюда же и «мега-клиент»: выделенная машина с пятью модемами — это тот же
агент с пятью воркерами, разбирающий очередь в пять линий. Никаких отличий
ни в коде, ни в схеме: меняется только число строк в таблице модемов
в `--settings`.

Ручные заявки встают в голову очереди — оператор не ждёт, пока пройдёт весь
плановый обход.

Очередь пересобирается на каждом перечитывании плана, а не хранится между
итерациями: то, что успел опросить коллега, просто исчезнет из неё само.

Когда модем не удалось открыть (порт исчез, занят чужой программой, не отвечает
на `AT`), воркер помечает его нерабочим и периодически пробует поднять заново.
Приборы при этом достаются оставшимся модемам; если рабочих не осталось вовсе —
агент просто ничего не опрашивает и продолжает пытаться поднять модем. Ничего
«возвращать» серверу не нужно: приборы не были ни за кем закреплены, они просто
остаются просроченными и достанутся тому, кто сможет.

### Закрытый браузер и спящий ПК

**Браузер ни на что не влияет.** Агент — служба Windows, она не знает про
браузер и работает при закрытой странице, при выходе пользователя из системы и
вообще без единого открытого окна. Страница нужна только чтобы смотреть.

**Спящий ПК — не работает ничего.** В S3 не выполняется ни одна программа, в
Modern Standby (S0) служба может жить, но сеть жёстко придушена, и полагаться
на это нельзя. Пока машина спит, её агент молчит.

Хорошая новость: в модели без очереди это почти не требует обработки.
Невыполненного «задания» не существует — есть прибор, который давно не
опрашивали. Он остаётся просроченным и будет опрошен, как только появится
живой агент: свой после пробуждения или чужой, если те же приборы отмечены
у коллеги. Ничего не копится и ничего не надо вытеснять.

Остаются две вещи.

**1. Машина, за которой закреплены приборы, настраивается на фоновую работу.**
Выделенной опросной машины может не быть вовсе — значит по расписанию звонит
обычный АРМ, и его надо к этому подготовить: см. «Настройка машины оператора»
ниже. Слоты расписания в любом случае разумнее ставить в рабочие часы.

**2. Проснувшийся агент не должен продолжать с того места, где заснул.**
Пока он спал, прибор мог опросить кто-то другой, а его мягкий захват давно
отпущен по таймауту. Поэтому при выходе из сна
(`SystemEvents.PowerModeChanged` → `Resume`) агент выбрасывает свою локальную
очередь и заново тянет план — расчёт просроченности сделает всё остальное.
Плюс страховка на стороне сервера: `log`/`data`/`finish` по прибору, захват
которого уже принадлежит другому агенту, отклоняются, и агент такой прибор
бросает.

### Отмена

Отменять нечего — прогонов как сущности нет. Единственное, что можно
остановить, это текущий сеанс: `POST /polling/devices/{id}/poll` с
`{"cancel": true}` снимает заявку на ручной опрос, а в ответе на очередной
`log`/`data` агент получает флаг `cancelled` и завершает сеанс штатно, с
`+++`/`ATH0`, а не обрывом линии.

### Язык, сборка и запуск

**Язык — C#, и это не предпочтение, а следствие.** Драйверы `calc*.dll` —
managed-сборки .NET Framework, которые надо загрузить **в свой процесс** через
MEF и вызывать у них методы напрямую. Это умеет только код на .NET. Python
(даже через pythonnet) дал бы тот же .NET-рантайм плюс хрупкий мост на каждом
АРМ; переписывать протоколы на Python — вариант C, отдельная большая работа.

- **Target:** `net48`. Драйверы собраны под `net40`, .NET Framework 4.8 их
  грузит как есть. .NET 8 не годится: `System.ComponentModel.Composition`
  в нужном виде, `System.ServiceModel` (атрибуты на `IPollDataService`) и
  привычки net40-кода живут в Framework.
- **Проект:** `agent/HlvAgent/HlvAgent.csproj` в этом же репозитории — тогда
  агент едет на офлайн-сервер тем же `make-bundles.bat`, что и всё остальное.
- **Зависимости:** только `System.IO.Ports` (в Framework встроен) и ссылки на
  `cask2.dll`, `libModels.dll`, `protobuf-net.dll` из `Devices\`. Ни одного
  NuGet-пакета — JSON для API пишется руками или берётся `Newtonsoft.Json`,
  который и так лежит в `Devices\`. Это принципиально: на офлайн-сервере
  восстановления пакетов нет.
- **Чем собирать:** на машине разработки уже стоят **VS Build Tools 2022**
  (`MSBuild\Current\Bin\MSBuild.exe`) и пакет ссылок **.NETFramework v4.8**
  (`Reference Assemblies\...\v4.8`). То есть Visual Studio не нужна:
  `msbuild agent\HlvAgent\HlvAgent.csproj /p:Configuration=Release`.
  **Первая задача шага 4 — собрать пустой net48-«hello world» этим MSBuild'ом
  и загрузить им `calcFloutecBP2.dll` через MEF.** Пока это не проверено на
  практике, весь вариант A остаётся выводом из чтения кода.
- **Что кладём рядом с exe:** папку `Devices\` целиком (из Ask2),
  `HlvAgent.exe.config` с теми же `bindingRedirect`, что в `cask2.dll.config`,
  и `agent.json` — URL бэкенда, ключ агента, интервал опроса очереди.

**Запуск — служба Windows.** Прод и так нативный Windows, никакого Docker.

- Внутри — обычный `ServiceBase` с фоновым потоком цикла; тот же exe с ключом
  `--console` запускается в консоли для отладки, это же и режим разработки.
- Установка: `sc create HlvAgent binPath= "...\HlvAgent.exe" start= delayed-auto`,
  `sc description`, `sc failure HlvAgent reset= 60 actions= restart/5000`
  (перезапуск после падения — важнее, чем кажется: агент на АРМ никто
  не сторожит). Отложенный старт — чтобы первая попытка связи не пришлась
  на ещё не поднятую сеть.
- **От чьего имени:** от учётки, у которой есть доступ к COM-порту и модему.
  На выделенной опросной машине, где за модемами никто не сидит, обычно
  подходит `LocalSystem`.
- **Автозапуск и сеть:** служба стартует до входа пользователя, модем на АРМ
  должен быть доступен без залогиненного пользователя. Это стоит проверить
  на первом же реальном АРМ — USB-модемы иногда «просыпаются» только
  в пользовательской сессии.
- Логи самого агента (не сеансов опроса) — в файл рядом с exe, с ротацией
  по дням; сеансы всё равно уезжают в БД через API.

### Настройка машины оператора

Выделенной опросной машины может не быть, поэтому по расписанию звонит обычный
рабочий ПК. Служба сама по себе фоновая, но по умолчанию Windows её усыпит
вместе с машиной и обесточит USB-модем. Всё нужное **делает `install.bat`** —
руками остаётся только то, что скриптом не выставляется.

#### Сон и пробуждение

```bat
:: не засыпать и не гибернировать от сети; экран пусть гаснет — это не мешает
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change disk-timeout-ac 0
powercfg /change monitor-timeout-ac 15

:: разрешить таймеры пробуждения (нужно, если машину всё же усыпляют вручную)
powercfg /setacvalueindex SCHEME_CURRENT SUB_SLEEP RTCWAKE 1
powercfg /setactive SCHEME_CURRENT
```

От батареи (`-dc`) настройки **не трогаем**: сажать ноутбук ради опроса
неправильно. Следствие честное — на батарее опрос не идёт.

Если машину всё-таки усыпляют на ночь, а слот стоит рано утром, добавляется
задача планировщика с галкой «Разбудить компьютер для выполнения задачи» за
5 минут до слота; сама задача ничего не делает (`cmd /c exit`) — она нужна
только чтобы разбудить машину, дальше работает уже запущенная служба.
На ноутбуке с закрытой крышкой или на батарее это не сработает, и строить
на этом расписание нельзя.

Полезно проверить `powercfg /a`: если в системе только Modern Standby (S0),
машина «спит» иначе — служба формально жива, но сеть придушена. Считаем такой
режим неработающим и отключаем сон совсем.

#### USB-модем не должен обесточиваться

Самая частая причина «ночью не опрашивалось, утром работает» — Windows
усыпляет USB-порт. Два места, и оба обязательны:

```bat
:: USB selective suspend = Disabled (GUID подсистемы USB и самой настройки)
powercfg /setacvalueindex SCHEME_CURRENT ^
  2a737441-1930-4402-8d77-b2bebba308a3 ^
  48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
powercfg /setactive SCHEME_CURRENT
```

Второе — уже у конкретного устройства: «Диспетчер устройств → модем/USB-хаб →
Управление электропитанием → снять „Разрешить отключение этого устройства для
экономии энергии“». Скриптуется через WMI-класс `MSPower_DeviceEnable`
(`root/wmi`), но надёжнее проверить глазами на первой машине.

Стоит также отключить быстрый запуск (`powercfg /h off`) — гибридное
выключение иногда оставляет USB-устройства в некорректном состоянии, и модем
после включения не отвечает до переподключения. Учтите, что эта же команда
выключает гибернацию.

#### Сеть в фоне

Хорошая новость: агент ходит **только наружу**, входящих соединений нет.
Значит не нужны ни правило брандмауэра, ни открытый порт, ни проброс.
Но три вещи ломают связь именно у службы, а не у пользователя:

- **Прокси.** Служба работает от `LocalSystem`, а прокси, настроенный в
  браузере пользователя, ей не достаётся. Если сеть требует прокси —
  либо `netsh winhttp set proxy ...`, либо явная настройка в `agent.json`.
  Про это узнают всегда одинаково: у оператора всё открывается, а агент
  «не видит сервер».
- **VPN, поднимаемый пользователем.** Если бекенд доступен только через
  VPN-клиент, который оператор запускает руками после входа, служба до входа
  и после блокировки сеанса связи не имеет. Тогда нужен либо VPN уровня
  машины, либо доступ к бекенду без него.
- **Старт до входа в систему.** Служба стартует раньше, чем пользователь
  логинится; сетевой стек к этому моменту поднят, но первые попытки могут
  прийтись на ещё не готовую сеть. Поэтому у службы отложенный старт
  (`sc config HlvAgent start= delayed-auto`) и обычный ретрай с паузой.

#### Модем должен быть виден из сеанса 0

Служба живёт в сеансе 0, без рабочего стола. COM-порты к сеансам не привязаны,
так что обычный USB-переходник или модем, отдающий `COMx`, доступен нормально.
Проверить стоит одно: модем должен появляться в системе **как COM-порт**, а не
как «мобильное широкополосное устройство», которому нужна фирменная утилита
в пользовательском сеансе. Такой модем службе недоступен, и это выясняется
на первой же машине.

#### Что делать, когда ПК всё-таки выключили

Ничего не ломается: задания ждут в очереди, лишние вытесняются как
`superseded`, а в админке видно `last_seen_at` агента. Нужен только явный
признак в интерфейсе — **«агент не выходил на связь N часов»** и **«приборы,
за которыми не стоит ни один живой агент»**. Без этих двух строк выключенный
на неделю ПК означает тихо недостающие данные, а это ровно то, ради чего
опрос и затевался.

### Раздача и установка на АРМ

Собирается **один exe**, но ставится **папка**: рядом с ним обязана лежать
`Devices\` (~30 DLL) — MEF читает её `DirectoryCatalog`'ом с диска, слить всё
в один файл через ILMerge не выйдет. Значит единица поставки — zip.

Состав пакета:

```
HlvAgent\
├─ HlvAgent.exe
├─ HlvAgent.exe.config        bindingRedirect как в cask2.dll.config
├─ agent.json                 URL бэкенда + ключ агента + интервал
├─ install.bat                служба + настройка электропитания и USB
├─ uninstall.bat
└─ Devices\                   ~30 DLL, копия из Ask2
```

**Первая установка автоматической быть не может** — создание службы требует
прав администратора на машине, из браузера это недостижимо ни в каком виде.
Автоматизируется всё остальное. Три канала, по возрастанию охвата:

1. **Пакет из админки (базовый вариант).** Админ заводит агента в HLViewer →
   бэкенд отдаёт готовый zip, в который уже подставлены URL и ключ этого
   агента. Оператору остаётся распаковать и один раз запустить `install.bat`
   от администратора. Никакой ручной правки конфигов, никакой пересылки ключа
   отдельным сообщением.

   Эндпоинт: `GET /polling/agents/{id}/package` (admin-only). Тонкость: в БД
   лежит только хэш ключа, восстановить его нельзя — поэтому **скачивание
   пакета = выпуск нового ключа** (старый перестаёт работать). Это и логично:
   пакет с ключом ходит по почте, и возможность отозвать его нужна.

2. **Групповая политика AD.** Домен в контуре уже есть (в проекте работает
   LDAP-аутентификация), так что при десятке-другом АРМ пакет раскладывается
   через GPO — startup-скрипт, выполняющийся от `SYSTEM`, то есть без участия
   оператора вообще. Ключ в этом случае один на политику либо генерится
   скриптом по имени машины.

3. **Автообновление самим агентом.** После первой установки служба уже
   существует, и подмена файлов прав администратора не требует — их хватает
   у самой службы. Агент в `hello` получает актуальную версию, при
   расхождении качает пакет, распаковывает во временную папку, проверяет
   контрольную сумму и перезапускает себя через маленький `updater.exe`
   (сама себя служба подменить не может — файл занят).

   Обновляем **только `HlvAgent.exe` и `Devices\`**, `agent.json` не трогаем
   никогда. Откат — предыдущая версия остаётся в `backup\` до первого
   успешного `hello` новой.

Порядок такой: сначала пункт 1 (он нужен в любом случае), пункт 3 — после
того как первая версия отстоится на паре машин, пункт 2 — если АРМ окажется
много. Версию агент шлёт в `hello`, поэтому в админке всегда видно, где какая
и кто отстал.

⚠️ Раздача пакета на много машин — это ещё и тиражирование `Devices\*.dll`
ДП «Укргазтех» за пределы одной установки Ask2. Технически ничего не мешает,
но согласование стоит проводить сразу с учётом числа машин.

### Запасной вариант, если DLL использовать нельзя

Если правообладатель не даст согласия — остаётся **C: свои реализации протоколов
на C# внутри того же агента**. Каркас (очередь, дозвон, логи, выгрузка) при этом
не меняется вообще, меняется только `DriverHost`: вместо MEF-композиции — наши
классы с тем же набором методов. Стоимость — по протоколу на прибор, начиная с
Флоутек ВР-2. Формат данных при этом уже известен: бинарные структуры разобраны
в `RESEARCH_NOTES_HostlibStructures.md`, а расшифровка кодов аварий и вмешательств
— в `FloutekAUparsing.GetAlarmMessage`/`GetAuditMessage`.

Вариант B (pythonnet) отброшен: тот же .NET-мост, но ещё и хрупкий на АРМ.

## Фронтенд

### Новая страница `/polling` — «Опитування приладів»

Регистрируется в четырёх местах (как любая страница здесь): маршрут в
`app/router.tsx:74-93`, путь в `KNOWN_ROUTES` (`:34-44` — иначе F5 выкинет на
`/overview`), пункт в `MAIN_NAV` (`components/AppShellLayout.tsx:35-43`) и ключ
в обоих файлах локалей.

Три вкладки (`SegmentedControl`):

#### «Агенти» — окно наблюдения

Главный экран, и он же самый новый для проекта. Слева список агентов, справа
лог выбранного.

По каждому агенту: имя и машина, состояние связи, **что опрашивается прямо
сейчас** (прибор, сколько уже длится сеанс), **что осталось в его очереди**
(список приборов), сколько опрошено за сегодня и сколько ошибок. Всё это —
из `POST /polling/agent/state`, который агент шлёт раз в 10–15 секунд.

Состояние связи считает **фронт**, по возрасту `last_seen_at`:

- моложе 45 с — «на зв'язку»;
- 45 с … 3 мин — «немає відповіді» (жёлтым), данные показываются как есть;
- старше 3 мин — «зв'язок втрачено» (красным). Агент не пропадает из списка,
  а остаётся в нём с этой отметкой и с последним, что успел сообщить, —
  плюс рядом ссылка «прилади, що лишились неопитаними», ведущая в третью
  вкладку с уже наложенным фильтром по этому агенту.

Такой же признак нужен и по логу: если у агента заявлен текущий прибор, а
строки лога не прибавляются несколько минут, показываем «опитування зависло» —
это ловит случай, когда служба жива, а сеанс встал.

Лог выбранного агента — **новый компонент `PollLogView`**: прокрутка с
автоскроллом, фильтр по уровню, подсветка ошибок. Живого лога в проекте ещё
нет, это единственный по-настоящему новый элемент. Читается инкрементально по
`seq` (см. `poll_log`), поэтому переключение между агентами дешёвое.

#### «Прилади»

Таблица всех приборов с GSM: ЛУМГ, имя, телефон, `auto_poll` и часы,
**коли опитано востаннє**, результат последней попытки и её код ошибки,
чей агент за него отвечает. Отсюда же кнопка **«Опитати зараз»** — она ставит
`manual_requested_at`, и ближайший агент возьмёт прибор вне очереди.

Строки с просрочкой (`last_poll_at` старше последнего слота) подсвечиваются,
и по этому признаку есть фильтр — это и есть замена «истории прогонов»
для повседневной работы: видно не «что запускали», а «что не сделано».

#### «Проблеми»

Сводка, ради которой всё и затевалось: приборы, **не опрошенные после
наступившего слота**; приборы, **за которыми не закреплён ни один агент**;
приборы с повторяющейся ошибкой (по `last_error_code`). Группировка по
коду ошибки даёт ту самую строку «10 приладів не беруть слухавку».

По образцу `UnpolledReport.tsx`: полоса фильтров (`CheckboxFilter` по ЛУМГ и
по коду ошибки), sticky-заголовок, `TablePagination`, экспорт в Excel того же
отфильтрованного набора. Оттуда же два правила: счётчики опций считаются по
всему результату, а не по отфильтрованному срезу, и состояние фильтров живёт
в родителе.

#### Как это обновляется

`GET /polling/live/stream` — тот же NDJSON, что и в `enterprise`: читается
ридером из `api/enterprise.ts:178-260` (там уже решены сборка строк из чанков
и `fallback` на обычный GET). События: `agents` (снимок состояния всех
агентов), `log` (новые строки по выбранному агенту), `ping` раз в 15 с.

Если стрим не поднялся — обычный `refetchInterval: 5000` на `/polling/live`,
как в `UpdateTab.tsx:40-45`. Экран наблюдения не должен зависеть от того,
пережил ли стрим прокси.

⚠️ `lib/apiClient.ts:23-30` задаёт таймауты по регулярке пути; `/polling/`
нужно внести туда, иначе сработает дефолт 30 с.

### Админка — три вкладки в существующем `AdminPage`

Группа **«Опитування»** в сайдбаре (`AdminPage.tsx:55-96`):

## Порядок работ

1. **Миграция + модели** (`poll_agent`, `poll_agent_device`, `poll_device`
   со всем состоянием опроса, `poll_log`, `poll_settings`, опционально
   `poll_attempt`) и CRUD настроек прибора/агентов + вкладки админки.
   Уже полезно само по себе: настройки связи из `ask2cfg.xml` перестают быть
   единственной копией. Цели пока только `gas_volume_calc`; колонки под
   `dpd_line_id` и `dpd_device_id` заводятся сразу, чтобы не переделывать схему.
2. **Импорт из `ask2cfg.xml`** — разовый скрипт `scripts/import_ask2_devices.py`,
   заполняющий `poll_device` по существующим `gas_volume_calc`. Отдельная,
   не сводящаяся к копированию часть — **таблица соответствия
   `gas_vol_calc_type.type_id` → `protocol_id`**, см. выше.
3. **Функция «пора ли опрашивать»** и агентские эндпоинты (`plan`, `state`,
   `start`, `log`, `data`, `finish`) + приём данных в DAO. Функцию писать
   первой и покрывать тестами: она одна заменяет весь бывший планировщик.
4. **Агент на C#** (`agent/`, net48): `ApiClient` → `ModemPool` → `ModemDialer`
   → `DriverHost` (MEF над `Devices\`) → `CollectingStore : IPollDataService`.
   Сперва один протокол — Флоутек ВР-2 (1070, `calcFloutecBP2.dll`, он же
   в примере `ask2cfg.xml`). Порядок внутри шага: сначала `CollectingStore`
   с записанным дампом обмена (без железа), потом дозвон, потом служба.
5. **UI**: окно наблюдения за агентами со стримом и живым логом, таблица
   приборов с «Опитати зараз», сводка проблем; плюс окно `--settings` у агента.
6. **Остальные протоколы** — КПЛГ, ВЕГА, Універсал, В25.
7. **Цели ДПД**: `dpd_line_id` и `dpd_device_id`, после сверки маппинга
   `V`/`Vru` → `dvst_alwrk`/`dvwrk_alwrk` на реальном приборе.
8. **Сверка с Ask2** на нескольких приборах, затем вывод Ask2 из опроса.

Отдельного шага «расписание в шедулере» больше нет — считать слоты некому,
кроме агента.

### Где это крутится

Продов два: **нативный Windows** (`D:\Metr\backend_prod`, запуск через

## Риски

- **Права на драйверы.** Технической защиты нет: лицензия проверяется только
  в окне логина Ask2, внутри `calc*.dll` её нет вовсе (проверено). Но DLL
  принадлежат ДП «Укргазтех», и их использование вне Ask2 стоит согласовать.
  Если согласия не будет — переходим на вариант C (свои протоколы в том же
  агенте); каркас не меняется, меняется только `DriverHost`.
- **`Protocol` — базовый класс с 250-методным `IPollDataService`.** Наша
  заглушка реализует девять реально используемых методов, остальное бросает
  `NotImplementedException`. Для нового протокола список может оказаться шире —
  добавляется по факту первого падения, но это ловится только на стенде.
- **CSD как услуга.** Дозвон данными живёт, пока оператор его поддерживает;
  запас прочности — сменный транспорт (в схеме уже есть `channel='tcp'`).
- **Один модем — одна линия.** Обход всего парка последовательно может не
  уложиться в окно между слотами; отсюда несколько модемов или несколько
  агентов.
- **Часы на АРМ.** Решение «слот наступил» принимает агент, поэтому убежавшие
  часы означают лишний или пропущенный опрос. Лечится тем, что `plan` отдаёт
  серверное время и агент считает по смещению, — но это надо не забыть
  сделать и проверить.
- **Сервер видит происходящее только со слов агентов.** Без телеметрии он
  не отличит «прибор сейчас опрашивается» от «никто не взялся». Поэтому окно
  наблюдения и признаки «зв'язок втрачено» / «опитування зависло» — не
  украшение, а единственный способ заметить, что что-то встало.
- **Пароли приборов открытым текстом** — принято по образцу DPD-кредов;
  если это неприемлемо, шифрование колонок нужно вводить отдельной задачей.
- **Настройки связи Ask2 могут жить в неразобранных 234 байтах `ASK.CFG`**
  (`GasVolumeCalcStruct.unk`). Если так — импорт п.2 упрощается; если нет —
  настройки заводятся руками или парсятся из `ask2cfg.xml`.
