## Context

Сейчас данные приборов попадают в HLViewer **только чужими руками**: Ask2 (WPF,
.NET Framework) звонит модемом на приборы, складывает бинарные hostlib-файлы, они
пакуются в zip на сетевой шар, а `scheduler_runner` раз в 120 с замечает свежий
архив и заливает его в Postgres (`update_hostlibs` → `S*R*D/R/A/U/S.*` →
`bulk_upsert_via_copy`). То есть HLViewer — конечное звено чужого конвейера.

Задача: **перенести сам опрос внутрь HLViewer** и убрать Ask2 из контура.
Пользователь из браузера должен запускать опрос вручную и по расписанию, видеть
живой прогресс и лог, а потом разбирать историю опросов и ошибки.

Согласовано с пользователем:

| Вопрос | Решение |
|---|---|
| Канал связи | **CSD — дозвон GSM-модемом** (ATDP<номер> → CONNECT). TCP пока не нужен, но транспорт делаем сменным |
| Где крутится опросчик | **Оба варианта**: модем на сервере И модем на ПК оператора |
| Как браузер достаёт модем на ПК | **Локальный агент** на ПК (служба/exe), сам тянет задания из API. Не Web Serial |
| Судьба Ask2 | **Сразу заменяем**, как только наш опрос заработает |
| Парк приборов | Разнородный: Флоутек ВР-2/ВР-3/ПКВ, КПЛГ, ВЕГА, Універсал, В25 и др. |
| Что читаем за сеанс | Часовые + суточные архивы, аварии + вмешательства, мгновенные + параметры |
| График | **Глобальные часы**, как `DPD_REFRESH_TIMES` (список `HH:MM`, правится в админке) |
| Драйверы приборов | **Вариант A** — переиспользуем готовые `Devices\calc*.dll` |
| Кто запускает опрос вручную | **Любой авторизованный пользователь**; настройки — админские |

Разнородность парка — определяющий факт: пять с лишним протоколов писать с нуля
нереально, поэтому основная ставка — **переиспользовать готовые драйверы Ask2**
(`Devices\calc*.dll`), а не переписывать обмен.

## Архитектура

Ключевое следствие «модем может стоять и на сервере, и на ПК оператора»: опрос
**не может** жить внутри `fastapi_v2`/`scheduler_v2`. Он выносится в отдельный
процесс — **агента опроса**, — а бэкенд становится диспетчером очереди.

```
браузер ──HTTP(cookie)──► FastAPI ──► Postgres: poll_device / poll_run / poll_task / poll_log
                             ▲                         │
                             │ X-Agent-Key             │ задания
                             │                         ▼
                    ┌────────┴────────┐        ┌───────────────┐
                    │ агент на сервере│        │агент на ПК опер│
                    │   COM3 + модем  │        │  COM5 + модем  │
                    └────────┬────────┘        └───────┬───────┘
                             ▼ ATDP<номер>             ▼
                          прибор                    прибор
```

Агент — один и тот же бинарник в обоих сценариях; разница только в месте
запуска и в том, какие приборы за ним закреплены. Агент **сам инициирует**
соединение с API (long-poll за заданием), поэтому ПК оператора не нужен ни
белый IP, ни открытый порт, ни VPN-вход внутрь.

### Почему очередь, а не «однострочный лок»

В бэкенде уже есть три экземпляра паттерна «одна строка + atomic conditional
UPDATE + heartbeat» (`update_job`, `dpd_refresh_job`, `dpd_line_job`). Для
опроса он не годится: агентов несколько, модем у каждого один, и задания надо
раздавать **по одному на агента**. Поэтому — настоящая очередь задач, но с тем
же идиомом захвата (`UPDATE … WHERE status='pending' … RETURNING`), без Redis.

Модем физически последовательный: агент берёт **ровно одно** задание за раз.
Это и есть естественный лок — параллелизм ограничен количеством агентов.

## Схема БД (новая миграция, `down_revision = "d1f3a5c7e9b2"`)

Ревизию выбрать в принятом здесь стиле (рукописный hex-подобный id, напр.
`e2a4c6b8d0f3`), не автогенерацией.

### `poll_agent` — кто может опрашивать

| колонка | тип | смысл |
|---|---|---|
| `id` | BigInt PK | |
| `name` | varchar(100) uq | «Сервер ЗЛВУМГ», «АРМ Іваненко» |
| `kind` | varchar(8) | `server` \| `client` |
| `key_hash` | varchar(255) | ключ показывается один раз при создании, хранится хэш |
| `branch_id` | FK→grmu_branch SET NULL | область ответственности |
| `active` | bool | |
| `last_seen_at`, `version`, `host` | | самоописание из `hello` |

**Граница ответственности.** Сервер отдаёт агенту список заданий с данными
приборов — и на этом его роль заканчивается. Сколько на машине модемов, на
каких портах, в каком порядке их занимать и что делать, когда все заняты, —
целиком дело службы на этой машине. Она же строит свою очередь и заливает
результат обратно.

Поэтому в схеме нет ни `poll_device.com_port`, ни списка портов у агента, ни
счётчиков занятости модемов: серверу нечего с ними делать, а лишнее знание
означало бы лишний код по обе стороны.

`baud` остаётся на приборе: скорость определяет прибор на том конце линии,
это не свойство машины. `tcp_host`/`tcp_port` — тоже на приборе, сетевой адрес
принадлежит прибору, а не звонящему.

### `poll_device` — как дозвониться до прибора

Это карточка **корректора**, а не линии. Корректоры в базе живут в трёх видах,
поэтому `poll_device` ссылается ровно на один из трёх (CHECK «заполнено ровно
одно» — приём уже применён в `virtual_line_member`):

| ссылка | что это | куда лягут данные |
|---|---|---|
| `gas_volume_calc_id` | прибор ЛУМГ из `ASK.CFG` | `hourly/daily/sys/edit_archive`, `params` |
| `dpd_line_id` | линия ДПД (текущий корректор берётся из истории `dpd_line_device`) | `dpd_line_hourly/daily_archive` |
| `dpd_device_id` | корректор промышленности (`ser_num + corector_type + ch_num`) | `dpd_hourly/daily_archive`, точка учёта разрешается через окна `enterprise_device` |

Смысл третьей строки — требование пользователя: **промышленность, которая
сейчас тянется через ДПД API, должна опрашиваться и напрямую по GSM.** Якорь
именно `dpd_device`, а не `enterprise`: корректор переезжает между точками, и
архив в этой части базы ключуется прибором (см. `enterprise_device.removed_at`).

⚠️ **Открытый вопрос — маппинг значений для целей ДПД.** `dpd_daily_archive`
хранит `dvst_alwrk`/`dvwrk_alwrk` (стандартный и рабочий объём), а `GasData`
из драйвера несёт `V`/`Vru`. Соответствие выглядит очевидным, но проверять его
надо на реальном приборе, сверив GSM-опрос с тем, что за те же сутки отдал ДПД
API. Кроме того `dpd_line_*` и `dpd_*` архивы хранят только объём, давление и
температуру — аварии, вмешательства и параметры, которые GSM-опрос принесёт,
класть в этой ветке некуда. Поэтому очередь работ: **сначала цели
`gas_volume_calc`, ветки ДПД — вторым этапом, после сверки.**

Остальные поля — калька с `ask2cfg.xml`, чтобы миграция настроек была
механической:

`enabled` · `auto_poll` · `poll_times` ·
`channel` (`com`/`tcp`) · `is_modem` · `phone` · `init_str` (деф. `AT&F`) ·
`dial_prefix` (деф. `ATDP`) · `baud` (9600) · `tcp_host`/`tcp_port` ·
`protocol_id` (деф. из `gas_vol_calc_type.type_id`) · `device_address` (деф. из
`gas_volume_calc.address`) · `access_code` · `access_password` ·
`answer_timeout_sec` (7) · `pause_between_ms` (400) · `repeat_count` (3) ·
`preamble_count` (0) · `depth_days` · `priority` (int) · `note`

Модемные и адаптерные поля — точная калька `cask2.Devices.COMChannel`
(подтверждено декомпиляцией): `modem_connect_timeout_sec` (40),
`modem_repeat_call_count` (3), `modem_pause_after_connect_ms` (400),
`is_adapter` · `adapter_line` · `adapter_speed` · `adapter_level_in` ·
`adapter_level_out` · `adapter_is_frequency` · `adapter_is_radio`.
Адаптер/радиоканал сейчас не задействован, но колонки заводим сразу —
иначе перенос настроек из Ask2 будет не механическим, а выборочным.

`access_password` — **plaintext-колонка, как `grmu_branch_dpd_credential.password`**,
и по тому же правилу: GET её никогда не отдаёт, PUT с пропущенным полем не
затирает. Шифрования в проекте нет, вводить его здесь — отдельная задача.

**Расписание — на приборе.** `auto_poll` (bool) отвечает на «опрашивать ли его
автоматически вообще», `poll_times` — свои часы этого прибора (список `HH:MM`,
NULL = взять глобальные из `poll_settings`). Глобальные часы остаются, но
становятся значением по умолчанию, а не единственным вариантом: обычный режим
— 1–2 раза в сутки, но конкретный прибор можно гонять чаще или в своё окно.

### `poll_agent_device` — кто какие приборы опрашивает

Замена прежнего `poll_device.agent_id`: связь **многие-ко-многим**
(`agent_id`, `poll_device_id`, PK по паре, обе FK CASCADE).

Так это работает у пользователя: на ПК обычно один модем на один порт, а
операторов с модемами несколько. Бэкенд спускает вниз список приборов, а каждый
агент в своих настройках отмечает галочками, какие из них берёт на себя — может
все, а может половину, поделившись с коллегой. Договариваются операторы между
собой, админ в это не вмешивается.

Отсюда два правила, оба обязательны:

- **Прибор не опрашивается дважды.** Если один прибор отмечен у двух агентов —
  задание всё равно одно, и достаётся тому, кто первым сделал `claim`; второй
  его уже не увидит. Это ровно то, что даёт атомарный захват, никакой отдельной
  синхронизации не нужно.
- **Прибор, не отмеченный никем, не опрашивается вообще.** Это тихая потеря
  данных, поэтому в админке нужен явный индикатор «ничей» и он же — в отчёте
  о прогоне.

### `poll_run` / `poll_task` / `poll_log` — история

- **`poll_run`**: `id`, `started_at`, `finished_at`, `status`, `trigger`
  (`schedule`|`manual`), `user_id`, `total`, `done`, `failed`, `error`.
- **`poll_task`**: `id`, `run_id` FK CASCADE, `poll_device_id` FK, `status`
  (`pending`→`claimed`→`running`→`done`/`error`/`cancelled`), `agent_id`,
  `slot_at` (см. ниже), `any_agent` (bool), `pinned_agent_id`,
  `claimed_at`, `started_at`, `finished_at`, `updated_at` (heartbeat), `attempt`,
  `error_code` (`no_dialtone`/`no_carrier`/`busy`/`timeout`/`crc`/`auth`/…),
  `error_text`, счётчики строк `rows_hourly`/`rows_daily`/`rows_sys`/`rows_edit`/
  `rows_params`, `connect_ms`, `duration_ms`.
- **`poll_log`**: `id`, `task_id` FK CASCADE, `ts`, `level`, `message`. Ретенция
  как у DPD-архива — прунинг старых строк в конце прогона.

`error_code` отдельно от текста — именно он даёт «выявить ошибки опроса»:
по нему строятся фильтры и сводка «10 приборов не берут трубку».

**`slot_at` — защита от дублей расписания.** Это отметка «задание за слот
такого-то числа такого-то часа», плюс частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX uq_poll_task_slot ON poll_task (poll_device_id, slot_at)
WHERE slot_at IS NOT NULL;
```

Шедулер крутится раз в 120 с и вычисляет наступившие слоты; без этого индекса
перезапуск шедулера или второй его экземпляр поставили бы задание повторно.
С ним повторная постановка просто ничего не делает. У ручных заданий
`slot_at IS NULL` — их можно ставить сколько угодно.

**`any_agent` / `pinned_agent_id` — кто вправе взять задание.** У заданий от
расписания `any_agent = false`: берёт только агент, у которого этот прибор
отмечен в `poll_agent_device`. У ручного «опросить сейчас» по умолчанию
`any_agent = true` — его подхватит любой живой агент с GSM, даже если прибор
за ним не закреплён. Если оператор хочет опросить именно своим модемом,
в форме запуска выбирается агент, и он пишется в `pinned_agent_id`.

Модели SQLModel обязательны **и** миграция: тесты строят схему из
`SQLModel.metadata`, а прод — из Alembic, и дрейф CI не ловит.

## Бэкенд

### Эндпоинты для UI (cookie-auth, мутации автоматически admin-only)

```
GET/PUT/DELETE /polling/devices/{calc_id}      настройки прибора
GET            /polling/devices/                список с фильтрами
GET/POST/DELETE /polling/agents/                реестр агентов (ключ отдаётся один раз)
GET/PUT        /polling/schedule                глобальные часы (как DPD)
POST           /polling/runs/                   запустить опрос (набор приборов) → 202
GET            /polling/runs/{id}               статус прогона
GET            /polling/runs/{id}/stream        NDJSON: progress + status + log + result
POST           /polling/runs/{id}/cancel
GET            /polling/runs/                   история, пагинация + фильтры
GET            /polling/runs/{id}/tasks         разбор прогона по приборам
```

Средний слой авторизации (`api/main.py:261-324`) делает **любой** POST
admin-only, а admin-only GET включается подстрокой в `_ADMIN_PATH_MARKERS`.
**Решено: запускать опрос вправе любой авторизованный пользователь**, настройки
приборов и агентов остаются админскими. Значит:

- `"polling/devices"`, `"polling/agents"` — добавить в `_ADMIN_PATH_MARKERS`;
- `POST /polling/runs/` и `POST /polling/runs/{id}/cancel` — явное исключение
  из admin-only списка (новый набор `_USER_WRITE_PATHS` рядом с `_PUBLIC_PATHS`,
  но с сохранением проверки сессии: исключение из «нужен админ», а не из «нужен
  вход»). Отдельным тестом закрепить, что viewer может запустить и отменить
  прогон, но получает 403 на `PUT /polling/devices/{id}`.

### Эндпоинты для агента (заголовок `X-Agent-Key`, не cookie)

```
POST /polling/agent/hello                  heartbeat раз в минуту: версия, хост
GET  /polling/agent/devices                весь список приборов + отметка «мои»
PUT  /polling/agent/devices                сохранить свой набор (список id)
POST /polling/agent/claim                  забрать свою пачку заданий (+ конфиг приборов)
POST /polling/agent/release                вернуть невыполненные задания в очередь
POST /polling/agent/tasks/{id}/log         пачка строк лога
POST /polling/agent/tasks/{id}/data        разобранные записи
POST /polling/agent/tasks/{id}/finish      итог: статус, error_code, счётчики
```

`GET/PUT /polling/agent/devices` — та самая пара, ради которой агент умеет
показывать свой список галочками. Ответ `GET` несёт, помимо `mine`, ещё и
`taken_by` — кем прибор уже отмечен, чтобы оператор видел, что коллега его
взял, и не дублировал. Набор хранится в `poll_agent_device` на бэкенде, а не
в локальном конфиге: иначе сервер не смог бы ни отсеять чужие задания в
`claim`, ни показать в админке приборы-сироты.

Эти пути надо вывести из cookie-миддлвары (по образцу `_PUBLIC_PATHS`) и
закрыть проверкой ключа агента — иначе default-deny вернёт 403 на каждый POST.

`claim` отдаёт агенту **всё, что для него готово**, а не по одному заданию:
очередь и раскладку по модемам строит сам агент.

```sql
UPDATE poll_task t SET status='claimed', agent_id=:a, claimed_at=now(), updated_at=now()
WHERE t.id IN (
    SELECT t2.id FROM poll_task t2
    JOIN poll_device d ON d.id = t2.poll_device_id
    WHERE t2.status = 'pending' AND d.enabled
      AND (t2.pinned_agent_id IS NULL OR t2.pinned_agent_id = :a)
      AND (t2.any_agent                                  -- ручное «прямо сейчас»
           OR EXISTS (SELECT 1 FROM poll_agent_device ad  -- своё по подписке
                      WHERE ad.agent_id = :a AND ad.poll_device_id = d.id))
    ORDER BY t2.priority DESC, t2.id
    LIMIT :batch FOR UPDATE OF t2 SKIP LOCKED)
RETURNING t.id, t.poll_device_id
```

Три условия читаются так: задание не закреплено за другим агентом; и либо это
ручной запуск (его берёт любой, у кого есть GSM), либо прибор отмечен в
настройках именно этого агента.

`FOR UPDATE SKIP LOCKED` — чтобы два агента, дёрнувшие `claim` в одну
миллисекунду, не подрались за строки, а второй просто взял следующие.

`:batch` — верхняя граница (скажем, 200), чтобы один агент не выгреб очередь
целиком, если приборы вдруг окажутся подписаны на всех. В обычной работе
подписки не пересекаются: у каждого оператора свой набор приборов, и брать у
него нечего.

Ответ несёт полную конфигурацию каждого прибора **и последние даты по каждому
типу архива** — драйверу они нужны для инкрементальной дочитки, и так агент не
делает отдельного round-trip'а на каждый `LastDate*`.

**Зависшие задания — по агенту, а не по заданию.** Раз агент забирает пачку и
работает по ней часами, «задание не обновлялось 15 минут» перестаёт означать
беду: последние в очереди и не должны обновляться. Поэтому в `pending`
возвращается то, что взято агентом, **который сам перестал отзываться**:

```sql
UPDATE poll_task t
SET status='pending', agent_id=NULL, claimed_at=NULL, attempt=attempt+1
FROM poll_agent a
WHERE t.agent_id = a.id
  AND t.status IN ('claimed','running')
  AND a.last_seen_at < now() - interval '10 minutes'
```

`hello` раз в минуту — и есть тот пульс, по которому это считается.
Отдельный предохранитель на сеанс: задание в статусе `running` дольше
`max_session_minutes` закрывается с `error_code = 'timeout'`.

> В парке пользователя **один модем — один прибор**, поэтому группировки нет.
> Ask2 её умеет (объединяет задания с одинаковым `ModemCallNumberPhone` и
> портом в один звонок), и если когда-нибудь появится объект с несколькими
> приборами за одним модемом — пачечный `claim` вернётся сюда как надстройка;
> схема БД к этому готова, `phone` уже лежит на приборе.

Зависшие задания (`updated_at < now() - 15 min`) возвращаются в `pending`
с инкрементом `attempt` — как stale-takeover в `update_job_lock`.

### Приём данных — прямо в DAO, без файлов

Агент отдаёт разобранные записи; бэкенд кладёт их существующими средствами:

```python
calc = await GasVolumeCalcDao(session).get_or_create(address=addr, lumg_id=lumg_id)
line = await LineDao(session).get_or_create(gas_volume_calc_id=calc.id, line=line_no)
await HourlyArchiveDao(session).bulk_upsert_via_copy(rows, HOURLY_ARCHIVE_CONSTRAINT)
# то же для daily / sys / edit / params
```

Альтернатива — писать hostlib-файлы и звать `update_direct()`. Отвергнута:
это лишний круг «сериализация → zip → распаковка → десериализация» ради тех же
самых DAO, плюс наследуется лимит имени файла (адрес — 3 цифры, линия — 1).
Идемпотентность даёт тот же уникальный констрейнт, что и при заливке из zip,
поэтому повторный опрос того же периода безопасен.

### Расписание

`maybe_poll_devices()` рядом с `maybe_refresh_dpd()` в `scheduler_runner.main()`,
с переиспользованием уже покрытого тестами `_last_due_refresh(now, times)`.
Планировщик только **создаёт `poll_run` с задачами**; звонит агент.

Часы теперь считаются **по каждому прибору**, а не одним списком на всех.
На каждом тике (120 с):

1. взять приборы с `enabled AND auto_poll`;
2. для каждого — его `poll_times`, а если NULL, глобальные из `poll_settings`;
3. посчитать последний наступивший слот `_last_due_refresh(now, times)`;
4. одним `INSERT ... ON CONFLICT DO NOTHING` поставить задания со `slot_at`
   этого слота — частичный уникальный индекс сам отсечёт уже поставленные.

Все задания одного тика складываются в один `poll_run` с `trigger='schedule'`;
если ставить нечего — прогон не создаётся вовсе. Правка расписания в админке
подхватывается за ≤120 с, потому что часы читаются из БД на каждом тике.

Пропущенный слот (сервер был выключен) не догоняется: пришёл в 14:05, слот
10:00 давно прошёл — задание всё равно поставится, потому что `_last_due_refresh`
возвращает последний наступивший слот суток, а индекс по `slot_at` не даст
поставить его дважды. Это осознанно: лучше опросить с опозданием, чем не
опросить.

### Стриминг прогресса

Повторяем `/enterprise/volumes/stream`: `StreamingResponse`,
`media_type="application/x-ndjson"`, `X-Accel-Buffering: no`, ping раз в 15 с,
последнее-значение для `progress` и очередь для редких событий.

Два обязательных довеска, иначе «живой лог» не поедет:
1. `StreamAwareGZipMiddleware` (`api/main.py:218-232`) сейчас исключает **один

2. nginx: `location /api/polling/` с `proxy_read_timeout 600s` — иначе дефолтные
   60 с рвут поток.

К словарю событий стрима (`progress` / `status` / `ping` / `result` / `error`)
добавляется **`log`** — строка с прибором, уровнем и текстом.

готовые `Devices\calc*.dll`.** Технически подтверждено, ниже — чем именно.

### Что показала декомпиляция

Разобраны `Ask2.exe`, `Devices\cask2.dll` (ядро), `calcFloutek.dll`,
`calcFloutecBP2.dll`, `CalcPKV.dll`, `calcKPLG.dll`, `CalcVega.dll`,
`calcUniversal.dll`, `libModels.dll`, `_licdrv.dll` (ilspycmd, вывод — только
в скретчпад сессии, в папку Ask2-218 ничего не писалось).

**1. Все драйверы — managed .NET Framework 4.0, плагины MEF.**
Каждая `calc*.dll` содержит `[Export(typeof(IDeviceRegister))] class RegCalcDev`
с методом `Register()`, который добавляет описание прибора в `Global.CalcsSource`
и экземпляры протоколов в `Global.Protocols`. Сами протоколы помечены
`[Export(typeof(Protocol))]`. Никакого нативного кода, никакого COM.

**2. Контракт драйвера — базовый класс `cask2.Devices.Protocol`** (в `cask2.dll`),
а не интерфейс. Виртуальные методы, которые переопределяет драйвер:

```
Init()
PollDayImplementation()        PollHourImplementation()     PollInstantImplementation()
PollPeriodicalImplementation() PollStatImplementation()     PollAlarmImplementation()
PollAuditImplementation()      PollBezopImplementation()    PollDailyAlarmsImplementation()
PollCalibrImplementation()     CorrectTimeImplementation()  ContractHourImplementation(byte)
WriteFHPImplementation(Passport)
Alarm(...) / Audit(...) / Bezop(...)   ← расшифровка кодов событий в текст
PollSessionBeginImplementation() / PollSessionEndImplementation()  ← только UId 42 и 5
```

**3. Как хост запускает драйвер** (`Ask2.Code.Poll.PollEngine.COMPortTread`):

```csharp
var proto  = Global.Protocols.Find(x => x.Id == device.ProtocolID);
var driver = (Protocol)Activator.CreateInstance(proto.GetType());
driver.dataStore = <реализация IPollDataService>;   // у Ask2 — WCF-клиент
driver.QItem     = queueItem;
driver.StartPoll(serialPort);                        // порт открыт и уже дозвонен
```

Четыре строчки — весь интеграционный шов. `StartPoll` внутри гоняет фиксированную
последовательность: WriteFHP → StatParam → Instant → Hour → Day → Periodical →
Alarm → DailyAlarms → Audit → Bezop → Calibrate → CorrectTime → ContractHour,
с `CheckBreak()` между шагами (там же логируется «No Carrier Detect» по падению
`serialPort.CDHolding`).

**4. Вся связь драйвера с БД — один интерфейс `IPollDataService`.**
Он большой (≈250 методов, WCF `[ServiceContract]`), но драйвер Флоутека трогает
девять: `LastRecordStatParm` ×2, `SaveStatParam`, `SaveGasPeriodical`,
`SaveGasInstant`, `SaveGasHour`, `SaveGasDay`, `SaveCalc`, `SaveAudit`,
`SaveAlarm`; плюс базовый класс зовёт `LastDateGasHour/Day/Instant/Alarm/Audit/
StatParm/Periodical`. Остальное — `throw new NotImplementedException()`.
**Это и есть точка врезки:** агент реализует `IPollDataService` как локальную
заглушку, копит записи в памяти и отправляет их нашим `POST …/data`.

**5. Глубина дочитки достаётся бесплатно.** Драйвер не решает сам, с какой даты
читать: он спрашивает `dataStore.LastDateGasHour(lineId)`, и если ответ старше
двух месяцев — сам ограничивает начало первым числом прошлого месяца; при
`QItem.IsPeriod == true` берёт явные `BeginPeriodDT/EndPeriodDT`. Значит наша
заглушка отвечает по данным HLViewer, и инкрементальный опрос работает без
единой строчки дополнительной логики. За период — то же самое через `IsPeriod`.

**6. Лицензии в драйверах нет.** `licAsk2.lic` читается ровно в одном месте —
`Ask2.Wnd.UserLogin.IsRegistrApp()`: десериализация `FileLic`, `ListUIdDevice`,
сверка `MachineName`/`UserDomainName`/`DateValid`. `_licdrv.dll` — это серийник
матплаты (`Win32_BaseBoard`) для `LicLoc.exe`. Внутри `calc*.dll` нет ни одной
ссылки на лицензию. Технически агент, грузящий эти DLL, проверки не встречает.
⚠️ Но это вопрос **юридический, а не технический**: DLL принадлежат
ДП «Укргазтех», и использовать их вне Ask2 нужно с их согласия. Решение —
за пользователем; технический план от него не зависит (см. запасной вариант C).

**7. WPF не мешает.** `cask2.dll` ссылается на `PresentationCore`/`WindowsBase`,
и `Global.GetValueResource()` читает `Application.Current.Resources`, но обёрнут
в `try/catch` и при отсутствии приложения возвращает `""`. То есть консольный
агент работает, просто тексты логов пустые. Лечится дёшево: создать `Application`
в STA-потоке и подгрузить `Resources/lang.*.xaml` — и логи снова человеческие.

### Насколько драйверы однородны и как их типы ложатся на нашу базу

Проверено по коду, три разных ответа.

**Поля данных — да, единый формат.** Все драйверы заполняют одни и те же классы
`cask2.Models.Data`: `GasData` (архивы и мгновенные), `EventData` (аварии и
вмешательства), `StatData` (параметры), `Passport`. `GasData` заметно богаче
наших таблиц (энергия, `V0/Q0/Vday0`, единицы, стандарты температуры), мы
кладём подмножество — ровно то, что и сейчас приходит в hostlib:

| hostlib `THostRecR` (29 Б) | наш `HourStruct` | колонка |
|---|---|---|
| `vH` | `volume` | `hourly_archive.volume` |
| `e` (`THostDataExt`, флаги) | `unknown` | не пишется |
| `dP` | `w_volume_dp` | `hourly_archive.w_volume_dp` |
| `p` / `t` / `ro` | `pressure`/`temperature`/`density` | одноимённые |

Поле `e` — не мусор: биты `0x40`/`0x20` это признаки «в записи была авария /
вмешательство», и читаются они **только** для протоколов 1000, 1020, 1060,
1070, 1075, 1077 (`ConvertHostlib.ConvertStructHourToGasData`). Там же
подтверждается уже сделанное на фронте: `dP` для счётчиковых линий несёт `Vru`,
а не перепад — отсюда «Макс./Мін. витрата» вместо «дельтаП».

**Коды аварий — нет, они свои у каждого семейства.** `EventData` несёт голый
`Code` плюс `ProtocolID`, а расшифровывает его драйвер: `FloutekAUparsing`
(~338 ветвей), `KplgAUparsing` (~284), `PKVAUparsing`, `UniAUparsing`. ВЕГА и
ВР-2 своего парсера не имеют: ВР-2 переиспользует `FloutekAUparsing`, то есть
у семейства Флоутек таблица общая.

Для нас это уже решено и ничего не ломает: `sys_type` и `edit_type` в нашей базе
ключуются парой `(код, gas_volume_calc_type_id)`, то есть словарь и так свой на
каждый тип прибора. На 04.09.2026 в базе разработки заполнено 9 типов —
от 215 до 1117 кодов аварий и 104–128 кодов вмешательств на тип. Агент отдаёт
сырой код, текст рисует существующий словарь, как и сегодня.

**Типы корректоров — не совпадают напрямую, нужна таблица перевода.**
Наш `gas_vol_calc_type.type_id` — это порядковый номер перечисления
`ConvertCFGtoXLS.Enum.TypeCalc` из `ConvertCFG.dll` (то есть код типа в
`ASK.CFG`), а не `ProtocolID` драйвера. Сверено поимённо: 9 = ФлоІнек,
29 = Флоутек-ТМ 3.4, 33 = Флоутек-ТМ ГОСТ586, 43 = КПЛГ, 47 = Флоутек ВР2,
49 = Данифлоу 7, 56 = Флоутек ПК-В.

Перевод делается в два шага, оба есть в коде Ask2:
`ConvertUId.GetUIdCalc(type_id)` → `UId` прибора, затем `UId` → протоколы,
которые зарегистрировал драйвер (`RegCalcDev.Register`).

| наш `type_id` | прибор | `UId` | протоколы |
|---|---|---|---|
| 5, 33 | Флоутек / Флоутек-ТМ ГОСТ586 | 33 | 999, 1000 |
| 9, 34 | ФлоІнек | 30 | — |
| 6, 35 | Флоукор | 20 | — |
| 29 | Флоутек-ТМ 3.4 | 60 | — |
| 47 | Флоутек ВР2 | 70 | 1070, 1071 |
| 48, 49 | Данифлоу СОУ112 / 7 | 42 | — |
| 56 | Флоутек ПК-В | 77 | 1077, 1078 |
| 0–4, 13–16, 27–28, 30–31 | семейство SF | 10 | — |

Две оговорки, обе важны для шага импорта:

1. **`type_id` не определяет протокол однозначно** — у одного `UId` их два
   (999/1000 у ВР-1, 1070/1071 у ВР-2, 1077/1078 у ПК-В: «РД» против «в.37»,
   обычный против «E_kWh», обычный против «споживач»). Поэтому `protocol_id`
   и хранится **на приборе**, а импорт может лишь подставить вариант по

2. **Таблица `ConvertUId` в имеющейся у нас `ConvertCFG.dll` устарела.**
   В ней нет ни 43 (КПЛГ), ни наших 59 (Флоутек ВР2 2020) и 61 (Данифлоу
   вер.8) — на них она возвращает 255 («неизвестно»). Эти три строки надо
   доопределить руками (или взять более свежую `ConvertCFG.dll`) и закрыть
   тестом: **у каждого типа в `gas_vol_calc_type` должен быть протокол**.

### Восстановленная последовательность дозвона

Повторяется `ModemRepeatCallCount` раз (деф. 3):

```
DiscardIn/Out; RTS=0; 50ms; DTR=0; 500ms
ReadTimeout=1000, WriteTimeout=500; DTR=1; 1000ms; RTS=1; 50ms
→ "ATE0V1\r"        500ms, ответ прочитать и выбросить
→ ModemInitStr+"\r" (деф. "at&f"), ReadTimeout=2000, ждать 2 с, искать "OK"
ReadTimeout = AnswerTimeOut*1000; сброс буферов
номер: если len>3 и не начинается с "atd" — приписать "atd"
→ "<номер>\r";  ReadTimeout = ModemConnectTimeOut*1000 (деф. 40 с)
цикл по 200 мс до таймаута, накапливая ответ:
    "CONNECT"/"CARRIER" + цифры → успех (цифры = согласованная скорость)
    иначе искать: NO CARRIER | BUSY | ERROR | NO DIALTONE | NO ANSWER | RING
    плюс аппаратный признак port.CDHolding
успех   → RTS=1, порт отдаётся драйверу
неуспех → DTR toggle, "+++\r", 500ms, "ATH0\r", следующая попытка
конец сеанса → 1.1 c, сброс буферов, DTR toggle, "+++", 1.2 c, "ATH0\r", 1.2 c, читать ответ
```

Отсюда прямо выводится словарь `poll_task.error_code`: `no_carrier`, `busy`,
`no_dialtone`, `no_answer`, `modem_error`, `connect_timeout`, `port_busy`,
плюс протокольные `crc`, `auth`, `timeout`.

### Один модем — один прибор

В парке пользователя за каждым прибором стоит свой модем со своим номером,
поэтому **задание = прибор = один дозвон**, и группировать нечего.

Ask2 группировку умеет — поток COM-порта берёт задание и подтягивает все
остальные с тем же `ModemCallNumberPhone` и портом, отрабатывая их за один
звонок. Мы это не воспроизводим: лишний код ради случая, которого нет.
Схема к нему готова (`phone` лежит на приборе), так что если появится объект
с несколькими приборами за одним модемом — пачечный `claim` добавляется
надстройкой, ничего не ломая.

**Следствие, которое надо считать заранее:** время опроса всего парка =
(число приборов ÷ число агентов) × (дозвон + сеанс). При ~2–4 минутах на
прибор один модем вытягивает 15–30 приборов в час. Если парк больше окна —
это решается не кодом, а вторым модемом и вторым агентом; приоритеты в очереди
задают, кто важнее, если окно всё же не закрылось.

### Что это добавляет к схеме БД

К `poll_device` — недостающие поля из `COMChannel`:
`modem_connect_timeout_sec` (40), `modem_repeat_call_count` (3),
`modem_pause_after_connect_ms` (400), `priority` (int),
`is_adapter` + `adapter_line`/`adapter_speed`/`adapter_level_in`/`adapter_level_out`/
`adapter_is_frequency`/`adapter_is_radio` (у Ask2 есть режим адаптера/радиоканала —
заводим колонки сразу, чтобы миграция настроек была механической).

Ответ `claim` несёт, помимо конфигурации прибора, **последние даты по каждому
типу архива** — их агент отдаёт драйверу через заглушку `IPollDataService`,
не делая отдельного round-trip'а на каждый `LastDate*`.

### Пул модемов и локальная очередь

Всё, что ниже, — внутреннее дело агента; сервер об этом не знает.

Агент забирает пачку заданий и кладёт их в свою очередь, отсортированную по
приоритету. Модемов на машине один (обычный случай) или несколько; **на каждый
модем — свой воркер**, который берёт из очереди следующее задание, когда
освободился. Заняты все — задания ждут в очереди, пока кто-нибудь не
освободится. Никакой диспетчеризации писать не нужно: очередь плюс воркеры
и есть всё поведение.

Ручное «опросить прямо сейчас» приходит с высоким приоритетом и потому встаёт
в голову очереди — оператор не ждёт, пока пройдёт весь суточный список.

Когда модем не удалось открыть (порт исчез, занят чужой программой, не отвечает
на `AT`), воркер помечает его нерабочим и периодически пробует поднять заново.
Задания при этом достаются оставшимся модемам; если рабочих не осталось вовсе —
агент **возвращает невыполненные задания** (`POST …/release`), чтобы они не
лежали мёртвым грузом до истечения таймаута, и продолжает пытаться поднять
модем.

`release` — единственная уступка в сторону сервера, и она себя оправдывает:
без неё выдернутый на АРМ модем означает, что подписанные на него приборы
не опрашиваются до конца суток молча.

### Отмена прогона

Раз агент держит пачку, отмену он должен как-то заметить. Ответ на любой
вызов по заданию (`log`, `data`, `finish`) несёт флаг `cancelled`; увидев его,
агент бросает остаток своей очереди по этому прогону и завершает текущий сеанс
штатно — с `+++`/`ATH0`, а не обрывом линии.

**`SettingsForm`** — то, чем оператор настраивает агента. `HlvAgent.exe
--settings` открывает окно с двумя вещами:

- **свои модемы** — таблица «порт + описание», строки добавляются из
  `SerialPort.GetPortNames()`, то есть из реально существующих на этой машине
  портов. Обычно строка одна. Хранится локально, в `agent.json`; сервер про
  это не знает и знать не должен;
- **свои приборы** — дерево «філія → ЛУМГ → прилад» с чекбоксами; тянется
  из `GET /polling/agent/devices`, показывает отметки «моє» и «взято
  Іваненком», по «Зберегти» уходит `PUT`.

Служба при этом не останавливается: новый набор приборов она увидит на
ближайшем `claim`, изменение состава модемов — перечитает и пересоберёт пул.

WinForms выбран потому, что он есть в net48 из коробки: ни одной новой
зависимости, а окно нужно простое. Там же показываются адрес бэкенда, состояние
связи и последние строки собственного лога — оператору должно хватать этого
окна, чтобы понять «работает / не работает», не открывая браузер.

Обязанности агента (не зависят от выбранного варианта):

1. `hello` при старте и раз в минуту: версия и имя хоста. Про порты и модемы
   сервер не спрашивает — это дело машины.
2. Цикл: `claim` → пришедшее сложить в свою очередь по приоритету → раздать
   свободным модемам; пусто — пауза и снова `claim`.
3. Сеанс (в воркере модема): открыть порт → дозвон → создать драйвер,
   подсунуть заглушку и `QItem`, `StartPoll(port)` → `+++`/`ATH0` → закрыть
   порт.
4. Каждый заметный шаг — строка лога, батчами по 20 или раз в 2 с.
5. Собранные записи → `data`, итог по каждому прибору → `finish` с `error_code`.
6. Порт закрывается и трубка кладётся **в `finally`** — брошенная линия
   означает, что следующий опрос не дозвонится.

### Язык, сборка и запуск

**Язык — C#, и это не предпочтение, а следствие.** Драйверы `calc*.dll` —
managed-сборки .NET Framework, которые надо загрузить **в свой процесс** через
MEF и вызывать у них методы напрямую. Это умеет только код на .NET. Python
(даже через pythonnet) дал бы тот же .NET-рантайм плюс хрупкий мост на каждом
АРМ; переписывать протоколы на Python — вариант C, отдельная большая работа.

- **Target:** `net48`. Драйверы собраны под `net40`, .NET Framework 4.8 их
  грузит как есть. .NET 8 не годится: `System.ComponentModel.Composition`
  в нужном виде, `System.ServiceModel` (атрибуты на `IPollDataService`) и
  привычки net40-кода живут в Framework.
- **Проект:** `agent/HlvAgent/HlvAgent.csproj` в этом же репозитории — тогда
  агент едет на офлайн-сервер тем же `make-bundles.bat`, что и всё остальное.
- **Зависимости:** только `System.IO.Ports` (в Framework встроен) и ссылки на
  `cask2.dll`, `libModels.dll`, `protobuf-net.dll` из `Devices\`. Ни одного
  NuGet-пакета — JSON для API пишется руками или берётся `Newtonsoft.Json`,
  который и так лежит в `Devices\`. Это принципиально: на офлайн-сервере
  восстановления пакетов нет.
- **Чем собирать:** на машине разработки уже стоят **VS Build Tools 2022**
  (`MSBuild\Current\Bin\MSBuild.exe`) и пакет ссылок **.NETFramework v4.8**
  (`Reference Assemblies\...\v4.8`). То есть Visual Studio не нужна:
  `msbuild agent\HlvAgent\HlvAgent.csproj /p:Configuration=Release`.
  **Первая задача шага 4 — собрать пустой net48-«hello world» этим MSBuild'ом
  и загрузить им `calcFloutecBP2.dll` через MEF.** Пока это не проверено на
  практике, весь вариант A остаётся выводом из чтения кода.
- **Что кладём рядом с exe:** папку `Devices\` целиком (из Ask2),
  `HlvAgent.exe.config` с теми же `bindingRedirect`, что в `cask2.dll.config`,
  и `agent.json` — URL бэкенда, ключ агента, интервал опроса очереди.

**Запуск — служба Windows.** Прод и так нативный Windows, никакого Docker.

- Внутри — обычный `ServiceBase` с фоновым потоком цикла; тот же exe с ключом
  `--console` запускается в консоли для отладки, это же и режим разработки.
- Установка: `sc create HlvAgent binPath= "...\HlvAgent.exe" start= auto`,
  `sc description`, `sc failure HlvAgent reset= 60 actions= restart/5000`
  (перезапуск после падения — важнее, чем кажется: агент на АРМ никто
  не сторожит).
- **От чьего имени:** на АРМ — от учётки, у которой есть доступ к COM-порту
  и модему; на сервере — `LocalSystem` достаточно.
- **Автозапуск и сеть:** служба стартует до входа пользователя, модем на АРМ
  должен быть доступен без залогиненного пользователя. Это стоит проверить
  на первом же реальном АРМ — USB-модемы иногда «просыпаются» только
  в пользовательской сессии.
- Логи самого агента (не сеансов опроса) — в файл рядом с exe, с ротацией
  по дням; сеансы всё равно уезжают в БД через API.

### Раздача и установка на АРМ

Собирается **один exe**, но ставится **папка**: рядом с ним обязана лежать
`Devices\` (~30 DLL) — MEF читает её `DirectoryCatalog`'ом с диска, слить всё
в один файл через ILMerge не выйдет. Значит единица поставки — zip.

Состав пакета:

```
HlvAgent\
├─ HlvAgent.exe
├─ HlvAgent.exe.config        bindingRedirect как в cask2.dll.config
├─ agent.json                 URL бэкенда + ключ агента + интервал
├─ install.bat                sc create/description/failure/start
├─ uninstall.bat
└─ Devices\                   ~30 DLL, копия из Ask2
```

**Первая установка автоматической быть не может** — создание службы требует
прав администратора на машине, из браузера это недостижимо ни в каком виде.
Автоматизируется всё остальное. Три канала, по возрастанию охвата:

1. **Пакет из админки (базовый вариант).** Админ заводит агента в HLViewer →
   бэкенд отдаёт готовый zip, в который уже подставлены URL и ключ этого
   агента. Оператору остаётся распаковать и один раз запустить `install.bat`
   от администратора. Никакой ручной правки конфигов, никакой пересылки ключа
   отдельным сообщением.

   Эндпоинт: `GET /polling/agents/{id}/package` (admin-only). Тонкость: в БД
   лежит только хэш ключа, восстановить его нельзя — поэтому **скачивание
   пакета = выпуск нового ключа** (старый перестаёт работать). Это и логично:
   пакет с ключом ходит по почте, и возможность отозвать его нужна.

2. **Групповая политика AD.** Домен в контуре уже есть (в проекте работает
   LDAP-аутентификация), так что при десятке-другом АРМ пакет раскладывается
   через GPO — startup-скрипт, выполняющийся от `SYSTEM`, то есть без участия
   оператора вообще. Ключ в этом случае один на политику либо генерится
   скриптом по имени машины.

3. **Автообновление самим агентом.** После первой установки служба уже
   существует, и подмена файлов прав администратора не требует — их хватает
   у самой службы. Агент в `hello` получает актуальную версию, при
   расхождении качает пакет, распаковывает во временную папку, проверяет
   контрольную сумму и перезапускает себя через маленький `updater.exe`
   (сама себя служба подменить не может — файл занят).

   Обновляем **только `HlvAgent.exe` и `Devices\`**, `agent.json` не трогаем
   никогда. Откат — предыдущая версия остаётся в `backup\` до первого
   успешного `hello` новой.

Порядок такой: сначала пункт 1 (он нужен в любом случае), пункт 3 — после
того как первая версия отстоится на паре машин, пункт 2 — если АРМ окажется
много. Версию агент шлёт в `hello`, поэтому в админке всегда видно, где какая
и кто отстал.

⚠️ Раздача пакета на много машин — это ещё и тиражирование `Devices\*.dll`
ДП «Укргазтех» за пределы одной установки Ask2. Технически ничего не мешает,
но согласование стоит проводить сразу с учётом числа машин.

### Запасной вариант, если DLL использовать нельзя

Если правообладатель не даст согласия — остаётся **C: свои реализации протоколов
на C# внутри того же агента**. Каркас (очередь, дозвон, логи, выгрузка) при этом
не меняется вообще, меняется только `DriverHost`: вместо MEF-композиции — наши
классы с тем же набором методов. Стоимость — по протоколу на прибор, начиная с
Флоутек ВР-2. Формат данных при этом уже известен: бинарные структуры разобраны
в `RESEARCH_NOTES_HostlibStructures.md`, а расшифровка кодов аварий и вмешательств
— в `FloutekAUparsing.GetAlarmMessage`/`GetAuditMessage`.

Вариант B (pythonnet) отброшен: тот же .NET-мост, но ещё и хрупкий на АРМ.

## Порядок работ

1. **Миграция + модели** (`poll_agent`, `poll_agent_device`, `poll_device`,
   `poll_run`, `poll_task`, `poll_log`, `poll_settings`) и CRUD настроек
   прибора/агентов + вкладки админки. Уже полезно само по себе: настройки
   связи из `ask2cfg.xml` перестают быть единственной копией.
   На этом же шаге — цели только `gas_volume_calc`; колонки под `dpd_line_id`
   и `dpd_device_id` заводятся сразу, чтобы не переделывать схему потом.
2. **Импорт из `ask2cfg.xml`** — разовый скрипт `scripts/import_ask2_devices.py`,
   заполняющий `poll_device` по существующим `gas_volume_calc`. Отдельная,
   не сводящаяся к копированию часть этого шага — **таблица соответствия
   `gas_vol_calc_type.type_id` → `protocol_id`**, см. ниже.
3. **Очередь + агентские эндпоинты + приём данных в DAO.**
4. **Агент на C#** (`agent/`, net48): `ApiClient` → `PortWorker` → `ModemDialer`
   → `DriverHost` (MEF над `Devices\`) → `CollectingStore : IPollDataService`.
   Сперва один протокол — Флоутек ВР-2 (1070, `calcFloutecBP2.dll`, он же
   в примере `ask2cfg.xml`). Порядок внутри шага: сначала `CollectingStore`
   с записанным дампом обмена (без железа), потом дозвон, потом служба.
5. **UI: страница, стрим, живой лог**, плюс окно `--settings` у агента
   (выбор своих приборов галочками).
6. **Расписание** в `scheduler_runner` — поприборные часы и `slot_at`.
7. **Остальные протоколы** — КПЛГ, ВЕГА, Універсал, В25.
8. **Цели ДПД**: `dpd_line_id` и `dpd_device_id`, после сверки маппинга
   `V`/`Vru` → `dvst_alwrk`/`dvwrk_alwrk` на реальном приборе.
9. **Сверка с Ask2** на нескольких приборах, затем вывод Ask2 из опроса.

## Риски

- **Права на драйверы.** Технической защиты нет: лицензия проверяется только
  в окне логина Ask2, внутри `calc*.dll` её нет вовсе (проверено). Но DLL
  принадлежат ДП «Укргазтех», и их использование вне Ask2 стоит согласовать.
  Если согласия не будет — переходим на вариант C (свои протоколы в том же
  агенте); каркас не меняется, меняется только `DriverHost`.
- **`Protocol` — базовый класс с 250-методным `IPollDataService`.** Наша
  заглушка реализует девять реально используемых методов, остальное бросает
  `NotImplementedException`. Для нового протокола список может оказаться шире —
  добавляется по факту первого падения, но это ловится только на стенде.
- **CSD как услуга.** Дозвон данными живёт, пока оператор его поддерживает;
  запас прочности — сменный транспорт (в схеме уже есть `channel='tcp'`).
- **Один модем — одна линия.** Часовой опрос всего парка последовательно может
  не уложиться в окно; отсюда несколько агентов и приоритеты в очереди.
- **Пароли приборов открытым текстом** — принято по образцу DPD-кредов;
  если это неприемлемо, шифрование колонок нужно вводить отдельной задачей.
- **Настройки связи Ask2 могут жить в неразобранных 234 байтах `ASK.CFG`**
  (`GasVolumeCalcStruct.unk`). Если так — импорт п.2 упрощается; если нет —
  настройки заводятся руками или парсятся из `ask2cfg.xml`.
